The World Rule in Hazel and in Fumola

Matthew, after ^report(25): do the same game logic that we've exported to Hazel in ^report(25), but now do a Hazel (best PRs for performance) against Fumola in Wasm, doing the same logic ... I especially want to compare the map-based version in Fumola (store world data in maps, not lists) --- so there's a chance at O(log N). This is the World room's rule (a step to the square beside), written in Fumola, and timed against Hazel with every performance change we have, at map sizes from 3x3 to 64x64 (^ticket(542)). The syntax of the two side by side is ^report(28).

Short answers. Node on the Ubuntu laptop, one process at a time, the median call, the mean of two rounds; every answer checked against the game's.

  1. Fumola with the world held in a HashMap is flat: about 0.54 ms and 450 steps a call at 64x64, the same as at 3x3. The map is built once, when the world changes (295 ms at 64x64), and each move passes four numbers and a direction and looks up one square. Fumola's HashMap is a persistent hash trie, O(log₃₂ N), constant at these sizes. That meets the goal set in ^report(25)'s next steps: O(1) or O(log N) in the world's size.
  2. Hazel has no map to do the same. Its best here walks a list: 254 ms at 64x64 with the world held in a closure, 346 ms passed in. Against Fumola's held map, that is 471x and 641x.
  3. Like for like, Fumola is faster on every version that grows. At 64x64, passing the whole map: 145 ms against Hazel's 346 (2.4x). Holding it as a list and walking it: 26.3 ms against 254 (9.7x).
  4. With only the neighbours passed, the two are the same: about 1 ms, at every size (1.35 and 1.27 ms at 64x64). There the call boundary is all there is.
  5. The boundaries differ. Hazel's library converts JS values into Hazel's. Fumola's wasm build takes only source text, so a passed map is written out and parsed every call: 281,427 characters at 64x64, most of its 195,144 steps. Holding the world in the instance avoids that, in either language.

What was measured#

  • Hazel at its best: its JS library built by GitHub from trial/r25-best (bce9b4e5d1): all 14 performance PRs, #2681's memo limited to depth 1 (proposed), and the library binding a call's argument in the environment (^ticket(539)). Timed with ^report(25)'s driver and rules: passed is the shipped rule, held the map held in a closure, neighbours the neighbours-only rule.
  • Fumola: its wasm build (fumola_wasm_bg.wasm, from 667a34d), in node through initSync, one instance per size. The rules are below; each call is fumola_eval_top of a call written as text, its answer read back from JSON and checked.

The Fumola rules#

The World rule, as the game's Hazel one reads (both, side by side): a step in a direction, the square there found, and a GoSquare if it has a way back. step stays in Nat: it checks an edge before stepping off it, since Fumola keeps Nat and Int apart (^report(28)'s traps).

func no_way(kind, d) { kind == "waterfall" and d == "N" };
func member(s, xs) { var found = false; for (x in xs.vals()) { if (x == s) { found := true } }; found };
func opp(d) { if (d == "N") { "S" } else if (d == "NE") { "SW" } else if (d == "E") { "W" } else if (d == "SE") { "NW" } else if (d == "S") { "N" } else if (d == "SW") { "NE" } else if (d == "W") { "E" } else if (d == "NW") { "SE" } else { "" } };
func step(c, r, d, cols, rows) {
  let up = d == "N" or d == "NE" or d == "NW";
  let down = d == "S" or d == "SE" or d == "SW";
  let left = d == "W" or d == "NW" or d == "SW";
  let right = d == "E" or d == "NE" or d == "SE";
  if ((up and r == 0) or (left and c == 0)) { null }
  else {
    let c2 = if (left) { c - 1 } else if (right) { c + 1 } else { c };
    let r2 = if (up) { r - 1 } else if (down) { r + 1 } else { r };
    if (c2 < cols and r2 < rows) { ?(c2, r2) } else { null }
  }
};
func decide(x, back, c, r) { if (member(back, x.ways) and (no_way(x.kind, back) == false)) { #GoSquare((c, r, back, #Done)) } else { #Done } };
func find_at(cs, i, n, c, r) { if (i == n) { null } else { let x = cs[i]; if (x.col == c and x.row == r) { ?x } else { find_at(cs, i + 1, n, c, r) } } };
func world_list(g, e) {
  switch (e) {
    case (#Way(d)) {
      switch (step(g.at_col, g.at_row, d, g.cols, g.rows)) {
        case (?(c, r)) { switch (find_at(g.cells, 0, g.cells.size(), c, r)) { case (?x) { decide(x, opp(d), c, r) }; case null { #Done } } };
        case null { #Done }
      }
    };
    case _ { #Done }
  }
}

The held versions: the world bound once in the instance, as a list (wl) and as a HashMap keyed by (col, row) (wm). A move passes four numbers and a direction.

What Hazel would need#

For the world's size to leave a move's cost alone, the rule must find a square without walking to it. Hazel's rules have lists and records, and no map. Three ways there:

  1. Pass only what the rule reads: the neighbours. Flat today, in both languages (answer 4), but the game must know what each rule reads.
  2. A map in Hazel, written in Hazel: a balanced tree keyed by (col, row), held as the world is held now. O(log N) evaluator steps a lookup. An estimate, not measured: a 64x64 world is twelve levels deep, and at a few dozen steps a level and about 3 µs a step (^report(25)), a lookup would cost about a millisecond, at any size near this one.
  3. A map built in, as Fumola's HashMap is a primitive over a persistent hash trie: one step a lookup.

That is ^ticket(540)'s question, every handler in O(1) or O(log N), now with a measured target.

How this was put together#

Node v22 on the Ubuntu laptop (Intel i7), one process at a time, pinned to two threads and niced. Fumola: drivers/measure.mjs (world.fum, held.fum.js), per size a fresh instance, three warm-up calls, then up to 60 timed (stopping after 2.5 s and at least 9), the median; its answer checked against the game's (GoSquare(c + 1, r, "W", Done)). Hazel: 025/drivers/r25.mjs on trial/r25-best's library, the same sizes. Two rounds each. The target cell is mid-map, moving east, as in ^report(25).
