One slider, three ways: what modular editing saves

A question about the two livelits branches. #2597 has no modular editing, and #2635 has it, from #2469 (modular editors). How long does one slider change take on a complex picture, the Livelit Playground's Full Body slide? The hypothesis: #2635 is much faster, especially in its UX outline mode, showing only the slider and the picture, because it doesn't reprocess the unrelated code. A third set-up separates the two halves of that hypothesis.

Short answers.

  1. Modular editing makes the change about 7× faster. From releasing the slider to the redrawn figure took a median of 8.6 s on #2597, and 1.2 s on #2635 with the whole program on screen (12 changes each). On #2597 the page analyzes the whole program again for every change: 5.4 s of statics per change, profiled. On #2635 it analyzes only the changed item, in 38 ms.
  2. Showing only the GUI, as it's built today, makes the change about 3× slower again: 3.5 s. In UX mode, the outline opens the slider and the picture as cells, and that divides the program into cells and the rest. The divided program costs more per change:
    • the worker's reuse check takes about 2 s instead of a few milliseconds, though it reuses exactly as much as with the program whole;
    • the page's autosave lands inside the change, turning the whole program into text and storing it (0.55 s);
    • the cells' livelit views run without their memo (0.46 s).
  3. So the hypothesis holds for analysis, not yet for display. Not reprocessing unrelated code is the big win, and statics per item already does it. Hiding the unrelated code saves nothing yet: with the whole program on screen, #2635 spends only 9 ms per change on the code view, because it is cached. And dividing the program costs more than hiding saves. With the fix in 5, the two about cancel: B takes as long as C.
  4. On #2597 the figure is rebuilt rather than patched: its elements are new after every change. That costs the page more, and it fooled the first measurements here (below).
  5. One fix in the worker's reuse check makes B as fast as C: 1.26 s against 1.23 s (medians of 12). It is on #2635 as cbdab791f5. The check now compares lexemes in the same memoized walk as structure, so the 2 s becomes 1–4 ms, with exactly the same reuse decisions (below).
  6. The worker's 2 s has one cause: the open picture cell's item depends on the slider, and in the divided program it is elaborated again after every change, with fresh ids. About 120 enclosing parts of the program then differ only by ids, and each takes the reuse check's slow path. With only the slider's cell open, those slow checks fall from 122 to 4 per change. Keeping a re-analyzed cell's ids stable would fix it. A GUI-only view that keeps the program whole would avoid all three costs.

The three set-ups

The Full Body slide draws a whole figure from about forty livelits: polygon editors for the shirt, pants, head, hair and shoes, choices and sliders for everything else, and a final ^picture of it all. Its text is the same on both branches. The change measured is one drag of the "arm length" slider, to a length not drawn before, so no change could be served from a cache of earlier pictures.

A: the whole program, analyzed again

On #2597, a slider change edits the program's text, since the livelit's model lives in it, and the page then runs statics on the whole program from scratch. That is 5.4 s of a 13.3 s profiled change. The page also rebuilds the whole code view (2.3 s) and turns the whole program into text (1.5 s). The worker's part, about a second, is the same as on #2635. This is the cost ^report(1) found on the much smaller Kids' Choice slide, where it was 3.5 s of statics against #2635's per-item 16 ms.

B: what dividing the program costs

The UX outline mode shows a GUI by opening its row as a cell: a small editor of its own. With cells open, the program is divided: the cells hold their items, and the rest stays in a base, and on every change the whole document is assembled again from them. Three costs follow, and none of them is in C:

  • The worker's reuse check, about 2 s per change. The worker reuses what didn't change by checking each part of a new request against its cache of the last one. With the program whole, that check is a hash lookup, and the whole check takes milliseconds. Divided, about 120 parts fail the hash lookup but turn out to be equal, and proving that costs about 2 s (below). The worker ends up reusing exactly as much as in C.
  • The autosave, 0.55 s. The app saves about a second after an edit. A change in C is usually over by then. In B it isn't, and the save, which turns the divided document into text and writes it out, lands on the main thread in the middle of the change.
  • The cells' livelit views, about 0.46 s. They are drawn without the view memo that the whole program's editor uses (live_html instead of memo_view), so they cost more than C's views of the whole program (0.16 s).

So B is slower not because it shows less, but because of how it shows less. Its picture and slider are as cheap to draw as C's, but they come from a divided program.

The reuse check, counted

To see what the worker's check was doing, a temporary build of #2635 counted its outcomes and printed them per request: is there a cached entry, does the hash match, and if not, are the two elaborations equal anyway? The hash covers ids as well as structure, so it differs when a part is rebuilt with new ids. The slow path then compares structure, which is cheap, since it is memoized across checks (0–5 ms in all). It also compares the two parts' lexemes, by building a trace of every node in each, and that is the 2 s. It is quadratic: the program is a chain of lets, each holding the rest of the program, and each of the 122 enclosing lets builds its trace of a subterm of about 6,400 nodes.

The parts that change ids are the ones that contain the picture's item, drawn. Its own text doesn't change, but with its cell open, the item is elaborated again after every change, and the nodes the elaboration adds get fresh ids (for example, a let renumbered 62e92200… → 2ed82400…). Close the picture's cell and the slow path falls to 4 checks. With the program whole, the item keeps its ids.

So there are two fixes, and either would remove most of the 2 s:

  • At the cause: a re-analyzed cell whose text didn't change should keep its elaboration's ids, or not be elaborated again at all. This is in how the divided program's statics treat open cells.
  • In the check: compare lexemes in the same memoized walk as structure, so a part that only changed ids costs one visit, not one per enclosing let. This also guards every other case where unchanged code arrives with new ids. The trap was first noted on the woods in #2609's finding 24, the performance tracking issue. The same full-trace comparison, Exp.fast_equal_with_lexemes, also gates several caches in the page.

A fix for the check, tried

The check's structural comparison is cheap because it is memoized across checks, and two subterms whose hashes match are equal without a walk. The lexeme comparison had neither. So Equality gets a ~lexemes option: every walker, for each sort of node, also requires the two nodes' lexemes to be equal, inside the same hash shortcut and memo. The reuse check calls Exp.fast_equal_hashed_with_lexemes instead of the structural comparison followed by two traces. Other callers of Equality are unchanged.

The decisions are identical; only their cost changed. With the check cheap, a change in B also finishes before the autosave fires, so the save stopped landing in the middle of it. B's range was 1.06–1.9 s, with one change at 3.8 s.

Profiled again with the fix (six changes, the last column of the table), the worker's part of a change in B is now smaller than in C (884 ms against 1,056), and the autosave and the text conversion are gone from the change. What B still spends beyond C is on the page: the cells' livelit views without their memo (449 ms against C's 163) and collecting the stream's state (340 against 204). Profiled, B's window is still 1.2× C's, though on the clock the two are within 3%: the profiler slows some code more than other code (as in ^report(4)), so these rows say where the time goes, and the clock says how much.

The fix is on #2635 as cbdab791f5. It adds a test that the one-walk check agrees with the trace check (the same term with new ids: equal; a lexeme-only edit: not; a real change: not). The existing test that a lexeme-only edit invalidates reuse still passes, as do the Evaluator (524), Evaluator.Incremental (46), IncrSlides (13), CallMemo (6) and Equality (8) groups.

#2597 has no lexeme comparison in its check: it predates 7de3875cd8, which added the comparison to dev after an in-place edit of @@ to @@@ showed the old operator's result. So #2597 has neither this cost nor that protection. Corrected on 2026-10-13: #2597 doesn't need that protection. Its terms carry no lexemes at all (they came to dev with 500c466b44, which #2597 lacks), and it turns an unknown operator such as @@ into a hole of its operands alone. So @@ and @@@ make the same term and the same result, and nothing can go stale. Its check is already the cheap one: the hash lookup, then the memoized structural walk. dev compares lexemes by trace on every check, and without the hash shortcut, so the same fix would suit it, together with the shortcut.

Also in these profiles: the page indexes the whole program

C's profile showed another cost that grows with the program. When the worker's partial results arrive, the page combines them with an index of the elaboration: where each expression starts and ends. That index is built again for each new evaluation, so once per slider change, and it took 204 ms of C's 949 ms page update, profiled. Only expressions get an entry, but the walk also rebuilt every pattern and type. 8717564a5f, also on #2635, stops the walk there: 115 ms per change, profiled over six changes, with no change in what the index holds (a new test checks that the page never falls back to its slower full walk). The clock can't see it: twelve changes in C took a median of 1.37 s, against 1.23 s before, inside the noise of a check that runs every 200 ms.

Measuring it: two things that went wrong first

  • On #2597, a slider set by a script does nothing. Setting the input's value and dispatching input and change events moves the slider on #2635, but on #2597 neither the label nor the picture changed in five minutes. A real pointer drag through WebDriver works on both, so every number here comes from real drags.
  • On #2597, the picture is rebuilt, not patched. A MutationObserver watching the picture's elements saw no change on #2597, because after a change those elements are gone, and the new picture is new elements. So the redraw is detected by content instead: every 200 ms the page compares the large pictures' markup with what it was before the drag. That works whether a picture is patched or rebuilt.

What next

  1. Bring the reuse check's fix to #2597, whose check has no lexeme comparison at all (above), and to dev, together with the hash shortcut. Corrected on 2026-10-13: there is nothing to bring to #2597 (above); dev remains.
  2. Keep an open cell's ids stable when it is analyzed again without its text changing, or don't analyze it again. With the fix the check is cheap, but those parts still miss the hash lookup on every change; stable ids would put them back on it, on any slide with cells open (above).
  3. Keep the autosave out of a change: save when the page is idle, not on a timer that can fall in the middle of an update.
  4. Give the cells' livelit views the view memo the whole program's editor uses.
  5. Or a GUI-only view that keeps the program whole, drawing just the chosen livelits from the whole program's editor instead of opening cells. That would avoid all three costs at once.
  6. A way to open a slide in UX mode from its address, for example ?mode=ux&show=arm_length,drawn. It would make these measurements, and demos, quicker to set up than clicking 41 rows off.

How this was put together

  • Builds: #2597 at a15c6f0b65 (with ^report(7)'s fix) and #2635 at 57c928cef4, then with cbdab791f5 and 8717564a5f, dev builds, served locally. The Full Body slide's text is identical on both.
  • Times: headless Firefox over WebDriver, a fresh profile per set-up, the slide opened at /fresh. Each change was a real drag of the "arm length" slider to a new length, the same twelve lengths in each set-up. The time runs from the slider's pointerup to the first moment a large picture's markup differed from before the drag, checked every 200 ms in the page. One set-up at a time, on one laptop.
  • B's set-up: the outline switched to 🖼️ UX mode, then every GUI row's 🖼️ chip switched off except "arm_length" and "drawn", by clicking the outline's own controls.
  • The reuse counts: a temporary build of #2635 (local branch perf/2635-reuse-diag, not pushed) that counted IncrEval.reuse_check's outcomes and printed them per request. Firefox copied the worker's console to a file (devtools.console.stdout.content). Its own sampling (an id trace of a few large subterms per change) slowed it, so the times in this report come from builds without it.
  • Profiles: the Gecko profiler, sampling every 1 ms, over three changes per set-up, and six more each for B with the reuse check's fix and for C with the index's. The windows run from each pointerup to its redraw, from marks the page set. The worker's evaluation is run_scheduled_slice, and its reuse check reuse_check.
