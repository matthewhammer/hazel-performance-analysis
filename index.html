Newest: the code editor re-checks only the tiles whose sorts can move: on each commit, a chunk's top-level tiles and its derivation tiles, not every tile it holds (on mega-4k, 25,852 → 270 tiles). Profiled, the code editor's part of a release went from 26 to 8 ms, but release to face moved only 3–5 ms (132 / 134 / 130 ms, with / without / with), which is within the noise. The profiler overstated this one. The gain grows with the program, not on this slide.

Before that: another profile. The face now waits only on the main thread: the commit, the redraw of the commit, then the redraw with the result. Its largest single item, in the worker, is fixed: reusing a cached result walked the whole reused code (the worker's evaluation 47 → 25 ms profiled). Release to face didn't move, since the worker is off its path.

Earlier: the three next steps from the 10-10 profile (the worker's responses 393 → 16 KB, no forced layouts, the problems panel per tile; release to face 140 / 142 ms, and about 3.2 s on #2597); a profile that found the result collector re-indexing the whole program (44 → 6 ms profiled); a view re-evaluates only the calls whose inputs changed (the face's first evaluation 43 → 12.5 ms); the evaluator's overhead (the face's view 60 → 42.5 ms, then a further 16–25% on a benchmark); requests carry only what changed (478 → 18.5 KB); #2597 is about 10× slower, without #2469; the worker's reuse check by Merkle hash (~410 → ~145 ms per release, and 2.7 → 0.41 s on a dev benchmark).

A slider change is the simplest thing a livelit can be asked to do: one number in one model changes, and something that depends on it redraws. In the Dress Up app it costs under a millisecond. In Hazel it now costs about 0.14 s, down from 4.6 s yesterday afternoon and from tens of seconds a few weeks ago. This report collects every performance problem we've found and fixed this fall, then looks at where the remaining time goes and what it would take to get to "immediate".

Try it

  • The same slides on #2597's live build (the full livelits branch), deployed from 5286ba3b10. It has these fixes too, but not #2469’s, so a Kids' Choice release there takes about 3.2 s (below).
  • Dress Up, the plain HTML/JS app this report compares against (now called Messed Up Dress Up, by its players).

The live builds take several seconds to load a slide. The numbers here were measured on local dev builds of the same commits, in headless Firefox.

Fixed with this profile: reusing an evaluation walked the reused code. When the worker reuses a cached result, it copies the cache entry of every node below it into the new cache, and it walked the whole reused subtree to find them: on a slider release, nearly the whole program, 16 ms of its 47 ms evaluation. Entries are recorded only for nodes evaluated outside any call, so the walk now stops at function bodies, as the result collector's index does (#2635 9129cd2774, #2597 5286ba3b10). The worker's evaluation went from 47 to 25 ms and its work per release from 69 to 45 ms. Release to face did not move (154 / 143.5 against 140 / 142 ms), since the worker is no longer on the face's path. On real caches (275 entries on mega-1k; a generated program on #2597) the copy equals the full walk, kept in the tests as the reference.

Fixed since: the code editor re-checked every tile's sort on every commit. The code editor draws the program in chunks of whole lines and reuses a chunk's drawing while the sorts its tiles show (the colours) are unchanged. Every commit brings new statics, and that re-checked every tile of every chunk: a lookup and a mold rebuilt per tile, over the whole program. A tile shows two sorts, and each can move only for some tiles: the parser's only for a chunk's top-level tiles, since below them sorts follow the code itself; and the one statics refine only for derivation tiles. A chunk now lists those tiles once, when it is drawn, and a commit re-checks only them (#2635 31502d1e3d; the chunked code view is #2469's, so there's nothing to port to #2597). Tiles re-checked per commit: mega-1k 4,115 → 36, mega-2k 11,624 → 114, mega-4k 25,852 → 270. On a Kids' Choice release, profiled: the check 16 → 0.3 ms, the code editor 26 → 8 ms. But release to face, twelve releases each, with the change, without it, then with it again: medians 132 / 134 / 130 ms, means 148 / 152 / 145. That's 3–5 ms, inside the spread of single releases (107–206 ms). A test checks over 36 real edits that the narrow check never reuses a chunk the full one would redraw, and that it does redraw when a sort moves. In the browser, an edited derivation program drew the same classes, token for token, as a fresh load of the same text.

Next, by payoff: find which of the request's values are new on each commit, probably the elaboration's spine down to the changed item and the statics table's changed paths, and keep their identity (15 ms of hashing, profiled; started); and make the redraw of the commit cheaper, since the face's redraw waits for it. After the sort check, take these profiled numbers as upper bounds: code made of many small calls looks several times costlier under the profiler than it is.

Done since that profile

  • The worker's responses carry only what the page doesn't have (#2635 90994d4443, #2597 526200d05a). The worker shares its messages the way requests are shared, by Merkle hash the other way round: a release's result went from 393 KB to 15–16 KB, the worker's encoding from 44 to 5 ms and the page's decoding from 14 to about 7 ms (profiled). If the page meets a reference it cannot resolve, it ignores the rest until the worker starts over, and asks for the evaluation again. One surprise, found with a timeline of the messages: the face is drawn from the stream message, and the big result used to land after that paint. The small one came 3 ms after the stream and was applied in the same frame, so the face waited for it; now a result that comes before the stream's paint is applied just after it. Back to back, release to face 154 / 152.5 → 148.5 / 145.5 ms; on #2597 about 3.9 → 3.2 s, and loading Shoes and Hair 12.9 → 10.8 s.
  • A redraw no longer forces three layouts to measure the page (#2635 3c270617e2, #2597 99bb432fdb). The probe displays beside the code are measured all at once, then placed, and written only when they move; the page's scroll width is only grown on a commit, read after the displays are placed, and measured exactly (which rewrites a document-wide CSS variable twice) 400 ms after things settle. The after-display effect went from 24 to 3.6 ms, and main-thread work per release from 246 to 207 ms (profiled). Release to face is unchanged: it fires at the DOM change, before these effects. The published width equals an exact measure once settled, grows at once under a 5000 px overlay, and shrinks back after it.
  • The problems panel reuses what it found for unchanged tiles (#2635 0560e5a124, #2597 f2b519fa52). Finding the incomplete tiles walked the whole program for every redraw with new syntax; each tile's answer is now remembered by the tile's identity, and an edit keeps the unchanged tiles. The panel went from 13 to 3 ms, the walk everywhere from 6 to 0.2 ms; release to face 147.5 / 144.5 → 140 / 142 ms.

Not fixed, found on the way: on #2597, after loading Shoes and Hair, the published scroll width is 1556 px where the content needs 2207, so a cell's background stops short. It was so before the change; the content grows after the last change that triggers a measure.

Where the 0.4 s went (an earlier profile)

This profile is from 10-10 afternoon, at 0.43 s a release, before the diff requests, the evaluator and view changes, and the collector fix; the section above has the latest. It is kept because it shows the shape of a release.

A slider release in Hazel is a program edit. The new model is written back into the program text, and everything that depends on the text runs again. In Dress Up, a release changes one field of one object and redraws.

Two things stand out:

  • The worker now takes about 145 ms per release (profiled), down from about 410 ms. Deciding what to reuse took about 280 ms of that; it now takes about 26 ms (below). Redrawing is now the largest cost, about 310 ms profiled. It isn't the browser's layout or DOM work (about 30 ms): it is Hazel rebuilding its view in JavaScript, once per redraw, and a release redrew six times (now four).
  • Everything else is many medium costs, each touching the whole program somewhere: re-building terms, encoding a 478 KB request, decoding a 383 KB response, redrawing the editor.

Statics, which a "skip statics" toggle would remove, is now 16 ms of it.

Finding · fixed

Incremental evaluation's reuse check cost more than it saved

The eval worker does evaluate incrementally: it keeps the last run's results and reuses them (#2606). But before each run it decides what it can reuse by comparing each cached entry's expression with the new program structurally, which is O(program) on every request. On a slider release that checking costs more than the re-evaluation it avoids:

This is the same shape as the problem #2661 fixed for types, where the evaluator compared two copies of the Html type at every node. It has the same fix: Merkle hashes on expressions, so that recognizing an unchanged expression is O(1).

The fix, and why hashing alone wasn't enough

A new Util.ValueHash hashes any immutable value by its structure, ids included, and keeps each object's hash. The reuse check now first asks whether the whole elaboration is the same build, and otherwise compares with a hashed equality, where identical subterms are equal without a walk.

That fixed Kids' Choice, but a benchmark on dev showed it was still quadratic. The program was 400 definitions, with an edit to the last literal. That edit sits inside every enclosing let, so every check along that spine still walked down to it, now also paying for hashing. The fix is to remember the answer for each pair of subterms compared, so every check after the first is a lookup.

The shortcut is sound only where identical terms really are equal: no renaming of variables, and no lookup environments or free-variable handler in the comparison. It's off for every other caller.

The fix is #2673 to dev, and on the livelits branches 5237161017 + 97c910f69c (#2635). Since then, the request shares its unchanged values with the last one, so the reuse check finds them the same by identity before any hashing.

Finding · fixed

A view re-evaluated every call, though one input changed

A livelit's view is evaluated again after each change of its model, and most of its calls are the calls of the last evaluation, made again. A new eye size on Kids' Choice changes the arguments of the face's two eye calls; sides_of, pieces, the brow, the mouth, teeth_of, sick_pile, mood and the face's three own sliders are called with what they were called with before.

Now a view's evaluation remembers its calls (Language.CallMemo). A call is identified by its function's body and the values of the variables that body reads, compared by structure with ids left out, since each evaluation mints new ones. A closure among those values compares by its code and the values it reads, not its whole environment, which holds the new model even for a helper that never reads it. "The variables a body reads" is every name that occurs in it as a variable: more than it reads, which can only cost a reuse, never give a wrong one. Only calls that took at least 40 steps are looked up or remembered. Only view evaluation uses it: a view's evaluation is pure (randomness and effects are commands, run after).

A recursive helper walking a picture's list is called on each tail, and each call's key put the tail in form again: now each node's form is remembered by identity, so shared tails are done once. Finding · fixed

Every release sent the worker the whole program

Each request to the eval worker carried the whole elaborated program and its statics table, 478 KB of Marshal, though a slider release changes one model value. Encoding it was about 52 ms (profiled) of the commit, on the main thread; decoding it was about 22 ms on the worker. And the decoded request was all new objects, so the worker's reuse check had to hash its way to what was unchanged.

Now both sides keep a table of the values the worker holds, keyed by the same Merkle hashes as the reuse check (Util.ShareCodec). The client sends a value the worker already has as a small reference carrying its hash, and the worker swaps each reference back for the value it kept. So a request is the changed paths plus references, and the worker's new request shares its unchanged values with the last one, which the reuse check sees by identity. If the tables ever disagree (a new worker, a cleared table, a request too deep to walk), the worker answers Resend and the client sends everything once; it also starts over when its table passes 200,000 entries.

And the first release after a load

The first slider release after a page load re-parsed the whole program, including the face's 8,612-piece definition: its commit took 245 ms instead of about 60. Loading fills the syntax pass's parse cache, but releases read statics' per-item cache, which stayed empty. The syntax pass now fills that one too (#2635 9d9d40dae2), and the first release's commit takes 55–63 ms like the rest. #2597 has no per-item parsing (it is #2469's), so this one doesn't apply there.

Finding

The full livelits branch is about 10× slower: it doesn't have #2469

The same Kids' Choice slider release, same machine, headless Firefox, median of 12: 3.76 s on #2597, about 0.35 s on #2635. Both redraw about as often per release. The difference is one step: after a livelit commits its new model, #2597 spends 2.3–2.7 s on the main thread before it can redraw, where #2635 spends about 60 ms. #2635 is #2597 plus dev plus #2469 (Modular editors, by Andrew Blinn), and it is #2469 that brings per-item statics (5e99ad8a4d), statics projection (64aeb86349), the code-view cache, the worker's stream throttle and slimmed responses (a05f8e5791), and the gates that keep idle frames and the pending sweep quiet (101757e1ed). None of these is on dev or on #2597.

So the fixes this report lists are on both branches, but a slider release is only fast where #2469 is too. The ways forward: measure and demo on #2635; port the smaller pieces of #2469 (the overlay gate, the code-view cache) to #2597 (per-item statics is the core of #2469, and porting it is the merge #2635 already is); or keep a livelit's change out of the text path (step 3 below), which would skip whole-program statics on #2597. On #2635 that step is no longer worth building: per-item parsing and statics already make the text path about 10 ms. A release on #2597 with the diff requests is still about 3.9 s, since statics, not the request, is its cost.

What the list has in common

Work on the whole thing, inside a loop over its parts

Per character, re-process the whole run. Per let, re-analyze the whole definition. Per click, walk the whole program. Per use, evaluate the whole definition. Per variable, copy in its whole value. Per redraw, evaluate every view. Each is linear on its own; inside a loop it becomes quadratic, and nested it becomes exponential.

Caches that key on object identity break silently

Per-item parsing, the layout cache and the statics cache reuse work when they see the same objects as last time. One helper that re-made every object (MapPiece) turned all of them off at once, with no error, just slowness. A hash of the content (TypHash) survives copies. Identity is cheaper when it holds; a hash is safer when something upstream might copy.

Measure where the user is

Node said statics took 4 s on slides that froze Firefox for 30–108 s. The fixes that mattered most were found by profiling Firefox itself, one interaction at a time (scripts/profile_interaction.py), and by counting work instead of timing it (--count-passes).

What limits a slider now, and what it would take

The plan as it stood at 0.43 s a release, with what became of each step. The latest profile sets the next ones. Profiled times; real time is about 1.7× smaller.

  1. Done: make the worker's reuse check cheap (~280 → ~26 ms). Merkle hashes on expressions plus remembered comparisons (above, #2673). The diff requests (4, below) now let it find most unchanged code by identity.
  2. Started: redraw less, and only what changed (~310 ms of view building). The page rebuilds its whole view after every action, and each message from the worker was its own action: a release redrew six times, though only one of the worker's four messages had anything new to show. Now the reuse plan and the final stream ride with other messages, and a release redraws four times (#2635 b481a876e1, #2597 d92f446112). Main-thread work per release went from 1,141–1,427 to 935–1,051 ms (profiled, two profiles each); the time until the face redraws barely moved, because the redraws removed were off that path. Then each redraw reuses what it drew from unchanged inputs (#2635 51df91d5d7, #2597 a15af020ea). The code view's cache had the whole syntax record in its key, which is rebuilt whenever a result arrives, so the code re-rendered on three redraws of every release for nothing; it now keys on the parts it reads. Closing each livelit event handler's environment, and printing each probe's samples, are now remembered by the identity of the value. Each redraw's own view building, median of 8 releases: preview 18.5 → 14 ms, commit 32 → 25.5, face 90.5 → 83, final result 16.5 → 15; all four 157 → 138.5 ms (−12%). What is left is mostly real work: evaluating the face's view (~70 ms), and the commit's new text.
  3. Dropped: keep a livelit's change out of the text path. The plan was to patch the elaborated program at the model's id and skip printing, re-parsing and re-checking, estimated at ~190 ms. Profiling steady-state releases before building it showed that path is now about 10 ms (profiled): MapPiece keeping identity, per-item parsing and per-item statics had already made it cheap. The one slow case was the first release after a load, which re-parsed everything; that is fixed (above). On #2597, without per-item statics, the step would still save its 3.5 s, but there porting #2469's statics is the better fix.
  4. Done: send the worker a diff, not the program. Cyrus's suggestion. Unchanged values now go as references by Merkle hash: a release's request is 18.5 KB instead of 478 KB, and release to face went from 359 to 229–273 ms (above). The response, up to 383 KB, is still sent whole.
  5. Started: make the face's own view cheaper, the largest single cost left. It is evaluated once per release, on the main thread (every other livelit's view comes from its cache), and the profile showed mostly the evaluator's own overhead, not the face's arithmetic. Two fixes so far: ids are minted as plain strings and compared as strings (7a5667e6f2), and the evaluator binds a run's constants once instead of re-applying itself to them at every node (857c293962). The face's view, warm, median of 8 evaluations over six releases: about 61 → 60 → 42.5 ms. A whole release (263 and 241.5 ms, median of 12, two runs) is within its noise. Then two more, on the evaluator's step machinery: its per-node stages are made once per run instead of eight closures at every node (2d35bb9e01), and two stages that only passed a value through no longer add a trampoline step for it (602498d7aa). The in-page probe could not see these (its medians vary by more than they save), so they were measured with a call-heavy program under node, the way views are evaluated, back to back:

    before the constants fix (7a5667e6f2)583–585 ms638–673 ms

    Then the bigger step: re-evaluate only the calls whose inputs changed, which took the face's first evaluation after a release from 43 to 12.5 ms.
  6. A faster evaluator for the views that do change (~170 ms). The face's view must run. The wasm spike (#2490) measured the evaluator about 4× faster under wasm_of_ocaml on fixed-precision work.

A release is now the livelit's own update, a per-item re-parse and re-check, a small request, a cheap reuse check, re-evaluating the face, and redrawing it: the same shape as Dress Up's path, with the face's evaluation as the largest piece. Dragging is already there: while the finger moves, a livelit runs its own update and view on the page without any of this, which is why the slider itself follows the pointer.

How these were measured

  • Headless Firefox over WebDriver, a fresh profile per run, dev builds of #2635, on Matthew's laptop. Wall times are from the slider's change event until the face's eyes redraw at the new size (scripts/slider_timing.py), four runs per build.
  • Stage times come from the Gecko profiler, started from Firefox's privileged context after load and bracketed with performance.mark (scripts/profile_interaction.py). Profiled runs take about 1.7× longer than unprofiled ones.
  • Message sizes: Worker.prototype.postMessage wrapped after load, with a listener for the worker's responses (scripts/worker_sizes.py).
  • Dress Up: sixty input events on its eye-size slider in the same headless Firefox; Firefox timers have 1 ms resolution, and the median was 0 ms, the worst 2 ms.
  • The dev reuse-check benchmark: a 400-definition program, evaluated, then its last literal edited with every id kept; only the incremental re-evaluation is timed, seven runs per build, under node.
  • Release-to-face timing without the debug panel (scripts/release_timing.py): twelve releases per build, cycling values, the median reported. Request sizes for the diff requests came from a temporary probe on the encoded message in post_evaluate. The face view's evaluation was timed by a temporary probe that, on each release, evaluated the view eight more times and logged the median of those eight; a build's number is the median of six releases' medians, and the baseline and the id change were measured back to back. The evaluator benchmark is a temporary test group: a program that builds a 2,000-element list of tuples through recursive helpers and recurses 3,000 deep, run through evaluate_open 15 times under node (the same js_of_ocaml build as the tests), two runs per build, all builds back to back. The call memo was timed by a temporary probe logging each release's first face evaluation, 12 releases per build, the build without it measured in the same session; its correctness check captured the face's SVG after each of 13 scripted slider changes on each build and compared them. The timelines of a release wrap the page's Worker.postMessage and listen to the worker's messages, and watch the face's eye with a MutationObserver, timing each against the release. Redraws were counted with a temporary probe logging each action and each view.
  • When a fix's gain is small, it is timed A/B/A: twelve releases with the change, twelve on the same commit without it (rebuilt in place, about 11 s), twelve with it again, back to back. The code editor's sort check is why: the profiler gave it 16 ms per release, and removing it saved 3–5 ms. Code made of many small calls slows down more under the profiler than the rest. The tiles re-checked per commit on the mega programs were counted by a temporary print in the test.
