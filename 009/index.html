Names and reuse: what fresh ids cost Hazel

How do fresh ids relate to lack of reuse in Hazel? An incremental system recognizes work it can reuse by identity, and identity is only as stable as the ids it hands out. Incremental Computation with Names (Hammer, Dunfield, Headley, Labich, Foster, Hicks and Van Horn, OOPSLA 2015), which Matthew co-wrote, asks this of Adapton: allocate with a fresh name and a re-run never matches the last one; allocate with a name derived from where you are, and it can. This issue measures what Hazel can tell us about it today, on the Livelit Playground's slides.

Short answers.

  1. Hazel has both kinds of id. Id.mk is a gensym: a counter and random bytes, unique every time. Id.derive, Id.next and IdTagged.fresh_deterministic make names: an id computed from a parent's, the same each time. The editor's tiles give the program's syntax names that last across edits. Statics and the evaluator mint almost everything else with the gensym (Figure 1).
  2. Analyzing the same program again renames what statics adds: 667 of Full Body's 111,462 nodes, and through the program's chain of lets, that changes the hash of 692 expressions though their structure is the same. No syntax id ever changes (below).
  3. Two sites in statics make most of them, and naming them as Adapton would, by where they are, cuts the renames from 667 to 85 and the changed hashes from 692 to 247 (below).
  4. But names do not change what is reused, only how. After a slider edit, Full Body reuses 336 parts with fresh ids or with names. Hazel's reuse check falls back to comparing structure, so a renamed part is still found the same, at a higher cost; naming moves 59 checks from that fallback to a hash lookup (below).
  5. And on these edits, incremental evaluation is no faster than starting over: Full Body 502 ms against 451 ms from scratch, Witch 857 against 791, Scenes 1,547 against 1,571 (node, medians of five). The edit's dependents are recomputed whatever the ids; the reuse a slider change could use is inside them.
  6. The evaluator mints by far the most: 461,422 ids to build the woods' picture of 33,847 nodes. The same picture evaluated twice is equal in structure but never by hash; the only ids the two share are the program's own (below).
  7. Between the page and the eval worker, fresh ids cost 11% of what results send, and requests twice what they could be, on eight woods figure moves. Results stay small because the worker's reuse hands back the very same objects: identity survives there through reuse, not through names (below).

At a glance

Where Hazel's ids come from

An id in Hazel is a 16-byte UUID. Id.mk makes one from a counter in its leading bytes and random bytes after it: a gensym, new at every call, which is what an incremental system cannot match from one run to the next. Id.derive(~salt, x), Id.next(x) and Id.mk_str(s) make version-5 UUIDs from a parent id or a string: names, the same every time they are computed from the same place. IdTagged.fresh_deterministic(prev_id, term) builds a node with Id.next(prev_id).

The program's syntax is named by the editor: each tile keeps its id across edits, so an item that did not change carries the same ids into the next analysis. Statics keeps those ids in the elaboration and mints ids for the nodes it adds. A few sites name them (function sugar, one definition site in Statics, module roots, padding in the pretty printer); most use IdTagged.fresh, which calls Id.mk, often through IdTagged.FreshGrammar. The evaluator gives every node it builds a fresh id.

Statics, run again: what gets renamed

Each slide was parsed once, so its syntax has one set of ids, and analyzed twice with Statics.mk_unmemoized, as the editor's per-item statics does for an item it analyzes again. (The memoized Statics.mk hands back the very same elaboration for the very same term, and so renames nothing.) This is the worst case: in the editor, only the edited item is analyzed again, and, in UX mode, the open cells (issue 008). The two elaborations have the same structure, node for node; walking them side by side:

Every renamed node is one statics minted; no syntax id changes. On Full Body they are, by kind: 42 case expressions and 42 holes, 84 constructor patterns and 84 constructor applications in patterns, 86 variable bindings, 59 ascriptions, 52 variable references, 47 field accesses, 45 applications, and 62 type nodes: about one set for each of the slide's livelit uses, and the types. They come from two places:

  • UserLivelit.mk_expand_dot_def builds each livelit use's elaboration: a case on the definition's expand, a Functional arm that applies it to the model and a Macro arm that is an ascribed hole. It is built with IdTagged.FreshGrammar, so every analysis gives it new ids.
  • StaticsBase.fresh_ascription inserts an ascription where a value's type differs from the expected one, also with FreshGrammar.

A renamed node changes the Merkle hash (Util.ValueHash, ids included) of every expression that holds it. A slide is a chain of lets, each holding the rest of the program, so one renamed node late in the chain changes the hash of every let above it.

Naming them: the experiment

Both sites can be named by where they are, as Adapton names an allocation:

  • the dispatch is renamed after it is built, each node's id derived from its parent's and its place among the parent's children, from a root derived from the use's own id. The code it embeds, the use's function and its model, keeps its ids. Two uses get different names; one use gets the same names at every analysis;
  • an inserted ascription takes its id from the expression it ascribes: Id.derive(~salt="ascription", Exp.rep_id(d)).

The renames fall from 667 to 85 on Full Body, and to 85 on every slide that uses the Drawing library: those 85 (62 of them type nodes) are the same on each of those slides, which points at the library's own analysis. Polygons has none left. The changed hashes fall from 692 to 247 (Figures 2 and 3). The experiment is on a local branch and was not committed; it is a measurement, not a proposal.

What the eval worker reuses, and what it costs

The worker evaluates incrementally: it checks each part of the new elaboration against its cache of the last run, by id, and reuses a part found the same with the same inputs. "The same" is the check from issue 008: one hash lookup, ids included, and if that fails, a walk comparing structure and lexemes, memoized. Here, each slide was evaluated, a slider's model was edited in place with every id kept (as the slider's commit keeps them), the edited program analyzed again, and evaluated against the first run's cache:

The parts reused are the same with fresh ids and with names: the structural fallback finds a renamed part the same, as a hash lookup finds a named one. Names only change the cost of finding it, which the one-walk check of issue 008 already made small. So in Hazel today, fresh ids do not cause lack of reuse; they cost the check.

The first incremental run is slower each time (the JavaScript engine warming up); the medians are what Figure 5 shows. Incremental evaluation is no faster here, with fresh ids or named. A slider's value flows into the drawing, so the parts that depend on it, the costly ones, are evaluated again; what is reused is mostly definitions, which are cheap. The reuse that would pay is inside those parts: the shapes of a picture that the slider did not move. Recognizing that needs the values computed inside an evaluation to carry identities from one run to the next, which is where the evaluator's ids come in.

This is node, with the whole program analyzed again. In the browser, the worker's request shares unchanged values with the last one and per-item statics keeps unchanged items, so more checks succeed by identity; whether the worker's incremental run beats a fresh one there is the next measurement.

The evaluator: an id for every node it builds

Counting Id.mk calls while the Scenes slide is evaluated up to its woods picture: 461,422 ids, the same number every run, for a picture of 33,847 nodes with 7,650 distinct ids (copies of a value keep its id). Nearly all of them belong to intermediate terms the evaluator builds and throws away; a fresh id is a 16-byte string, made at every step that builds a node: part of what each step of evaluation allocates.

Evaluated twice, the two pictures are equal in structure and differ by hash. Of the second picture's nodes, 26,266 have an id that is also in the first, and every one of those is an id of the program itself, a literal carried into the picture. The rest are new each time. So a cache keyed by a value's hash can never recognize the same value computed again. That is why the views' call memo erases ids from its keys before comparing, and why the worker's results share well only where its reuse handed back the very same object.

Between the page and the worker

Requests and results cross between the page and the worker with their already-sent values replaced by references, by hash, ids included (Util.ShareCodec). A build that counted, for each message, the slots of the values it sent, and the slots it would have sent if every part equal in structure to one already sent had also gone as a reference, moved the figure in the woods eight times:

About 2,900 parts a move went to the page as references. They are the parts the worker reused: the same objects as last time, so the same hashes. What a result sends beyond them is mostly new: the moved figure and the picture's list built around it. A request is twice what it could be, from a small base (about 5,400 slots a move, against 749,480 when the slide loads): the edited item, analyzed again, with what statics adds renamed (above).

What next

  1. Name what statics adds. The two sites measured here, the livelit use's dispatch and the inserted ascriptions, then the 85 left from the library. It removes most renames of an item analyzed again, so its unchanged parts pass the reuse check by hash; whether it closes the gap measured in requests is to be measured. A small change, with a test that two analyses give the same ids and two uses different ones.
  2. Mint fewer ids in the evaluator. 461,422 for one picture, most for terms thrown away: minting an id only when a node is kept, or naming it by its provenance, is part of the per-step allocation the evaluator still has.
  3. Names inside evaluation, for the reuse that would pay. Reusing the shapes a slider did not move, inside a part that is evaluated again, needs values that keep their identity from run to run: names for what evaluation allocates, in the sense of the 2015 paper. That is a design question, for a note with Cyrus before any code.
  4. Measure the worker's incremental run in the browser, against a fresh one, with per-item statics and shared requests as they are there.

How this was put together

  • Build: #2635 (livelits × modular editors) at c4e64060f1, with measuring code on a local branch, not pushed: counters in the reuse check and in Id.mk, the naming experiment behind a switch, and the message counts in ShareCodec.
  • Statics and reuse: node, the test build, the slides of the Livelit Playground. Each slide parsed once (FastParse, MakeTerm), analyzed with Statics.mk_unmemoized; the edit replaces one integer literal, a slider's model whose value occurs once in the slide, keeping its id. Renamed means the same position in both elaborations with different ids; a hash changed means Util.ValueHash.same was false for an expression whose structure was equal.
  • Times: node's CPU time (Sys.time) after a full collection, five runs alternating the incremental and the fresh evaluation, in one process, fresh ids first, then named.
  • Evaluation: Evaluator.evaluate_open, as the page evaluates a view, of the Scenes slide cut at its picture and ending with the picture.
  • Page and worker: headless Firefox over WebDriver, the Scenes slide (woods), eight moves of the "across" slider by input events, six seconds apart, the console copied to a file. A slot is a field of a value as js_of_ocaml lays it out (an array); a part counts as equal in structure by a hash that skips 16-character strings, taken for ids.
