Where the Gap Comes From

Matthew, on ^report(27)'s Figure 1: seems to say that Hazel and Fumola are less than 3x apart in this situation. How would you attribute the difference in performance? Is it Wasm vs JS -- or more than that? Both use a small-step evaluation system, for a language with purely-functional, higher order data. Let's draft a report WIP --- looking more into the contrast and how it shows up with actual analysis of each system, while running the same programs. Eight small programs, written the same way in both languages, timed, step-counted and profiled (^ticket(545)).

Short answers. More than wasm against js. The first three are the causes, each measured below; the last two are where the target and the boundary come in.

  1. Hazel takes fewer steps, and each costs far more. For the same loop, Hazel's evaluator makes about half as many passes as Fumola's machine takes steps (14,009 against 27,025 for count(1000)): Fumola's steps are finer. But a Hazel pass costs about 2.6 µs and a Fumola step about 0.13 µs, some 20 times as much. Net, Fumola is 10x faster on the loop and 6.5x on calls.
  2. A Hazel step pays for the editor around it. Every term the evaluator visits, values included, goes through five stages: state merging, a reuse check, probe sampling, recording effects, then the rule itself. On the loop, the rule is 7% of the time; garbage collection is 36%, and the stages and their trampolines 37%. Fumola's machine keeps values apart from syntax and steps a continuation: one match, no stages.
  3. On lists, Hazel's costs grow with the list, so the gap does too. Two causes, both found here:
    • A function handed to JS carries its captured values as text. When Hazel's JS library returns a function, it writes the function's environment into its body (finish: Substitution.in_exp), so a list the function holds becomes a list literal inside it, evaluated again, element by element, at every call: 0.234, 1.14 and 3.94 ms for lists of 100, 1,000 and 3,000, where Fumola's stays at about 0.291 ms. Called from inside Hazel, the same function costs 27 passes at every size: Hazel's evaluator holds values in O(1); its library does not. This is what holding the world cost in ^report(27), and what ^ticket(540) was chasing.
    • A list loop is quadratic. Each iteration that passes the growing list on pushes its type, [Int], over every element again, minting a fresh id for each part and then keeping none of them. Building and summing 3,000 numbers: 4,591 ms in Hazel, 24.7 ms in Fumola, 186x.
  4. Where js does show, it is in Hazel's ids. A fresh id is a UUID written into 16 bytes, and js_of_ocaml turns bytes into a JS string by hand: about three quarters of minting an id, and 46% of the list loop's time. A native build would copy 16 bytes. Wasm costs Fumola 1.2x to 1.5x against its native build on the same runner.
  5. Hazel's boundary is the cheaper one. Passing in 3,000 numbers from JS costs Hazel 0.931 ms; Fumola, which takes only source text, parses them in 5.65 ms. For ^report(27)'s map of 4,096 cells: 80.3 ms in Hazel, most of Fumola's 148.

The programs#

Each written the way the other language would, as near as the two allow: recursion over numbers, and lists built from pairs (Hazel's ::, Fumola's ?(x, rest), since Fumola's [...] are arrays). No type annotations in either; Hazel infers and inserts its own. A held list is built once, outside the call, and captured: in Hazel by a closure, in Fumola by a top-level binding. Every call's answer is checked.

Fumola (drivers/kernels.fum)

A Hazel pass is one trip through the evaluator's stages for one term; a step is a pass that rewrote the term (the rest found a value). Fumola's step is one transition of its machine. Hazel's steps for count(1000): 9,007, nine an iteration (a lookup, an application, a comparison, a subtraction, ...); Fumola's: 27,025, twenty-seven an iteration, since its machine writes down every frame it pushes and pops.

Read across a row. Where the passes grow with n and the µs a pass stays put (count, fib, h_walk), the gap is steps times the cost of each: a constant factor, about 12x to 10x. Where the µs a pass climbs with n (sumbuild: 3.9, then 17.6, then 49.3 µs), some pass is doing work that grows with the data. And where the passes themselves grow with a list the program never walks (h_ref: 3,008 passes for one reference to 3,000 numbers), the evaluator is visiting it anyway.

What a Hazel step costs#

Hazel's evaluator is small-step in what it records, but it runs as a recursive descent: evaluate asks for each subterm's value by calling itself, on a trampoline so deep recursion does not overflow JS's stack. Every call goes through the same stack of stages (src/language/dynamics/Evaluator.re):

  1. eval_5_state_merge: at the top level, a fresh state, merged back after.
  2. eval_4_reuse: has this term's value been kept from a previous run? (the incremental evaluation of live programming)
  3. eval_3_record_probe_sample: is this term probed? Open and close a sample.
  4. eval_2_until_final: step until the term is final.
  5. eval_1_effects: run the step's effects on the state (stack frames, pattern matches for probes), update the reuse map.
  6. eval_0_main: the rule itself (Transition.re), with the stages above as its way of evaluating subterms.

The stages are what make Hazel's live features work: probes, the stepper, results kept across edits. They run for every term, including numbers and lists that are already values. Profiles of the calls alone (set-up excluded), on a build that keeps OCaml's names (embed-520's dev build, 2026-10-21; its evaluator is the same shape as the best build's):

  • The loop (count): garbage collection is the largest part. Each pass allocates: a trampoline closure per request, a new state record, a fresh term for each result. The rule is 7%.
  • The list loop (sumbuild): 46% minting fresh ids, and most of the rest pushing types and collecting the garbage. The next section is why.
  • One reference to a held list, from JS (h_ref): all of it in the stages and their trampolines: 3,008 passes, one for the list and one for each number in it, each finding a value and taking no step (why: the next section).

Why lists cost more in Hazel#

A function returned to JS re-evaluates what it holds#

Using a list that a function holds costs a pass for every part of the list, when the function is called from JS: let u = held in k, (held, 1), case held | _ => k end, (fun x -> k)(held) all cost n + 8 passes for a list of n, twice that for two references, and three passes a pair for a list of pairs. It does not matter how the list was made (built in Hazel, passed in from JS, annotated). A reference in a branch not taken costs nothing.

A trace of every pass (a copy of the dev build, patched to log the term each pass visits) shows why. The function's body, as the library calls it, is not let u = held in k but let u = [1, 2, 3, 4] in k: the held list has become a literal in the body. Evaluating a literal list evaluates each element, as it must for [1 + 1, f(x)].

> Closure(Let(...))                 the body, after the call's FunAp
  > Let(...)
    > ListLit[4]                    held, written in as a literal
      > Atom  < Atom Final (no step)   ... once for each element
    < ListLit[4] Final (no step)
  > Closure(Var(k))  < Final

The literal is written in by the library, not the evaluator. Evaluator.evaluate finishes every result with finish = e => e |> Substitution.in_exp(env) |> Exp.replace_all_ids, which turns a closure (a function and its environment) into a closed term by substituting the environment's values into the body. HazelLibCore.to_js then wraps that closed term as a JS function. Inside Hazel nothing is substituted: a closure keeps its environment, and a variable's lookup is one step (Transition.re marks a looked-up list final and returns it as it is). Measured with the counter build, the same held function called 100 times by a Hazel loop against called once from JS:

So this cost is the library's, and the fix is the library's: hand JS the closure as the evaluator left it, environment and all, rather than its finished form; the call then applies the closure as Hazel would. That is the same move as ^ticket(539)'s change for a call's argument (bind it in the environment, do not write it in), made for what comes back. Fumola never has this problem: its values are not syntax, so there is nothing to write back into a body.

A loop re-types its list#

Hazel is gradually typed: it inserts type ascriptions where it infers types, and pushes them through values as it runs. In build(n - 1, n :: acc) the accumulator meets [Int] once an iteration (the counter build shows one Ascription step per iteration), and the push walks the whole list, with a fresh term and a fresh id for each element (src/language/dynamics/transition/Ascriptions.re):

| (ListLit(ds), List(ty)) =>
  let ds' = List.map(d => recur(Asc(d, ty) |> DHExp.fresh), ds);
  unchanged(ds, ds')
    ? Some(e)
    : Some(IdTagged.fast_copy(DHExp.rep_id(e), ListLit(ds') |> DHExp.fresh));

In the profile of sumbuild(1000), 60% of the time is spent inside Ascriptions.re, the ids it mints included. When every element already has the type, unchanged gives back the list as it was, so the result is right and small; but the n wrappers and their n ids were made first and are thrown away. Over a loop of n iterations that is about n²/2 ids. #2681's memo (^report(26)) skips this push for a value it has seen at the top of an annotated call; an accumulator is new at every iteration, so it is never seen.

Two changes would help, neither tried yet: check whether a part needs the push before wrapping it (an element of type Int that is an Int needs nothing), and mint ids only for parts that change.

And a fresh id is dear under js#

Hazel's ids are UUIDs (src/util/Id.re). Minting one is already cheap in OCaml terms (a counter written into 16 bytes, not a random draw), but Uuidm.v4 copies the bytes into a string, and under js_of_ocaml bytes are an array and a string is a JS string, so the copy is a loop over 16 characters building a JS string. In the list loop's profile, 46% of the time is under Id.mk, and three quarters of that is js_of_ocaml's caml_subarray_to_jsbytes and caml_convert_bytes_to_array. This is the one place where the target clearly costs Hazel: natively it would be a 16-byte copy.

What a Fumola step is#

Fumola's machine (crates/fumola_semantics/src/lib/vm_step.rs) is a continuation machine: its state is the current continuation (an expression to evaluate or a value to return), a stack of frames, and an environment, a persistent hash map (im_rc) from names to values. Values are their own type, apart from syntax, so a list held in the environment is a pointer that is never looked into again. A step is one transition: push a frame, pop one, look a name up. Steps are many and small (twenty-seven an iteration of count) and cost about 0.13 µs each in wasm. Fumola's incremental machinery (Adapton's graph) is paid only when a program uses it; Hazel's stages run for every term. do big { ... } runs a region without writing its intermediate states down, about twice as fast again (Adapton/fumola#128, not used here).

One thing found on the way: a deep Fumola answer crashes the wasm instance (memory access out of bounds), and the instance is unusable after (^ticket(549)). Holding a deep value is fine; sending it out is not. It is not the printer, for a list: data answers go out through a structural translation (translate and nested in crates/fumola_wasm/src/lib.rs, calling each other once a nested value, into a serde_json tree), and that recursion runs out of wasm's stack. The printer (format_one_line, used for values with no structural translation, such as a function) recurses too, and runs out sooner. Measured, a fresh instance for each (drivers/deep_answer.mjs):

^report(27)'s Figure 1, read again#

At 64x64 (4,096 cells), the World rule:

  • Passed in: Hazel 341 ms, Fumola 148 ms (2.3x). Close, for different reasons. Fumola spends most of its time parsing the map, written out as 281,427 characters of source text, every call (195,144 steps). Hazel spends 80.3 ms bringing the map over from JS (a rule that ignores it, given the same map: ^report(25)'s idU), records and lists of text being dearer to convert than the numbers of skip, and the rest, 261 ms, walking the list, about 64 µs a cell, a few dozen passes each. The finder's annotation costs one look-up a call, not a walk: #2681's memo knows every tail of a list it has checked.
  • Held as a list and walked: Hazel 256 ms, Fumola 28.7 ms (8.9x). Steps times their cost, as in h_walk, plus, in Hazel, the held world re-evaluated as a literal at every call, since the rule is a function the library returned to JS.
  • Neighbours only: about 1 ms each. The boundary is all there is, and the two boundaries cost about the same for a handful of cells.

So the Figure's under-3x lines are the ones where something other than stepping dominates. Where stepping dominates, the gap is 12x to 10x; where Hazel's per-use walks and re-typing apply, it grows without bound.

What next#

  1. Keep closures whole across the library (^ticket(547)): functions returned to JS as the evaluator left them, not finished, on a trial branch stacked with ^ticket(539)'s, and these programs measured again: h_ref should be flat. Then ^ticket(540)'s balanced tree for the World rule can pay off: a held world, O(log N) a move.
  2. Push types without copying (^ticket(548)): check before wrapping in Ascriptions.re, and measure sumbuild again: it should become linear.
  3. Cheaper ids under js: an id that is a JS string from the start, or an integer, and what that does to the loop's 4%, the list loop's 46%.
  4. Fumola's deep answers (^ticket(549)): send answers out without recursion, both the structural JSON and the printer, or stop at a depth with a clear error (an issue for Adapton/fumola, not filed yet).
  5. The per-pass cost of the stages when nothing is probed and nothing reused: a fast path for terms that are already values would skip all five.

How this was put together#

Node v22 on the Ubuntu laptop (Intel i7), one process at a time, pinned to two threads and niced. drivers/kernels.mjs runs the programs: Hazel through its JS library (Hazel.run once, then each program a JS function, called with n), Fumola through its wasm build (fumola_eval_top of the call's text, pinned build 2ec634b5df). Three warm-up calls, then up to 60 timed (stopping after 2.5 s and at least 5), the median. Hazel's library: trial/r25-best (all the performance PRs, ^report(25)) for times, trial/r25-stats (the same with a counter, Hazel.stepCounts()) for passes. Profiles: drivers/prof_ref.mjs records only the calls, through node's inspector, on a dev build with OCaml's names and source positions; drivers/profiles.py splits them by source file. GitHub: Adapton/fumola branch bench/545-contrast builds Fumola natively (crates/fumola_wasm/examples/kernels.rs, calling the same fumola_eval_top) and as wasm, and runs both and Hazel's best build, three rounds interleaved. One round on the laptop so far: read single differences under about 10% as noise.
