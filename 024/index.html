The subsystems, and what flows between them

Hazel is a structure editor: the program is always a tree of tiles, and every edit leaves a program that can be typed and run. An edit passes through five subsystems in a fixed order, all on the page's main thread except evaluation (Figure 1).

  • The editor. The program is a segment: a list of pieces (tiles, grout, whitespace, projectors), where each tile has an id and child segments (Base.re:3-28). The zipper is the caret's place in that tree (ZipperBase.re:13-20). A key press becomes an Action, wrapped as Perform (CodeEditable.re:343), and Perform.go edits the zipper, consulting the previous statics as it does (Editor.re:146-184).
  • MakeTerm. Turns tiles into a term, Exp.t, and gives each term node the ids of the tiles that make it up (MakeTerm.re:290-306). For statics it first fills in the pieces missing from the visible segment, its canonical completion (MakeTerm.re:1997-2013).
  • Statics. One recursive walk over the whole term, from an empty map (Statics.re:4350-4381), that types and elaborates at once. It returns the info map, one record per expression id, and the elaborated program. It runs on the main thread, 225 ms after typing stops, or at once after a projector's commit (CodeWithStatics.re:93-141).
  • Evaluation. The elaborated program goes to the eval worker by postMessage, with a slice of the info map (EvalInfo) and the previous run's cache (EvalResult.re:250-293). The worker evaluates in slices; for a program of at least 2,500 EvalInfo entries it also reuses earlier results, keyed by expression id, and below that it evaluates from scratch (WorkerServer.re:300-304).
  • Results back. The worker's messages come back as actions: values, probe samples and test results. The page updates its model, recalculates without running statics again, and redraws, error marks included.

Every reader looks a record up by id. So whichever analysis writes a node's record last decides what the cursor inspector, the error marks, completion, projectors, probes and the worker's reuse check all see (StaticsBase.re:10-11: add_info is a plain Id.Map.add). That is what gives #2651 its architectural side: it changes which analysis writes last inside a module's definition (the PR).

On dev statics is one walk of the whole program per refresh. Andrew Blinn's #2469 (Modular editors), not yet on dev, adds DefStatics: statics per top-level definition, with the context passed from one to the next, so that an edit re-analyzes the edited definition and those that read a name it changed (DefStatics.re:3-102469 head). Inside one definition the walk is the same, so #2651 applies under both.

The representations they share

The subsystems pass five things along: the segment, the term, the info map, the elaborated program and EvalInfo. What ties them together is the id. MakeTerm gives a term node its tile's id, statics files the node's record under that id, EvalInfo keeps the node's elaboration under it, and the worker keys its probe samples and cached results by it (Figure 2). A term made inside statics can carry an id it borrows: the ModuleExp case builds its let with the ModuleExp's own id (IdTagged.re:175-183, used at Statics.re:2737-2741), so that let's record lands where the binding's would.

An edit's round trip, and the worker's messages

Figure 3 follows one key press. Every action goes through an update phase and then a calculate phase (Main.re:73-110):

  1. The key becomes an action, Perform(Insert(c)) (CodeEditable.re:343), and Editor.Update.update runs Perform.go on the zipper with the statics of the previous refresh (Editor.re:146-184).
  2. The calculate phase asks the debounce whether to run statics. While typing it says Defer and starts a 225 ms timer; when the timer fires it dispatches a refresh that says Force (CodeWithStatics.re:104-140). Statics runs on Force, on an edit that is not deferred, or when the set of probes changed (CodeWithStatics.re:200-204).
  3. CachedStatics.init parses the zipper for statics, runs Statics.mk over the whole term, and derives the error ids, warning ids and probe targets (CachedStatics.re:188-226, CachedStatics.re:99-135). The time it takes shows in the debug sidebar's Statics timer (CodeWithStatics.re:188).
  4. Editor.Update.calculate refreshes the completion buffer from the record at the caret, the syntax cache and the probes (Editor.re:186-230).
  5. EvalResult.calculate projects the info map to EvalInfo every time it runs (EvalResult.re:270-275). It queues a request for the worker only when the elaborated program (compared ignoring ids), the settings or the probe targets changed (EvalResult.re:251-261, EvalResult.re:279-293).
  6. The worker answers with messages, Figure 4; each comes back as an action, which updates the result and recalculates without running statics again.

The worker's protocol is in WorkerServer.re:7-89. A request carries, for each editor, the elaborated program, the EvalInfo slice and the previous run's incremental cache, Marshal-encoded. The worker posts an Ack at once; then a ReusePlan, its prediction of what it can reuse, for every batch it plans (WorkerServer.re:495-506, WorkerServer.re:431-439); then a Stream message after each slice of 5,000 steps (WorkerServer.re:271); and last a Result. Below 2,500 EvalInfo entries the prediction is empty and the worker evaluates from scratch, without the previous run's cache (WorkerServer.re:300-304, WorkerServer.re:315-319, WorkerServer.re:366). The page restarts a worker that has not acked in 5 s (15 s from a cold start), up to three times, and gives up on a request after 20 s (WorkerClient.re:5-11). Its callbacks become result actions (EvalRequest.re:6-41).

Reuse is where statics and the worker meet, for a program of at least 2,500 EvalInfo entries; a smaller one is evaluated from scratch, with no reuse check (WorkerServer.re:300-304, WorkerServer.re:366). At each expression, the worker's reuse check compares the elaboration EvalInfo recorded at that id with the one the cached result was computed from, then the provenance of the free variables in the record's co-context, then the probe targets (IncrEval.re:313-353). So what statics writes at an id matters to the worker as much as to the editor: the same last write is what both see.

Inside statics

The walk

Statics is one function, uexp_to_info_map, called on every expression (Statics.re:191-201). It takes the context (what is in scope), the expected type, the term and the map, and returns the term's record, its elaboration and the new map. Each case analyzes the children it needs, passing context and expected type down and getting records and elaborations back, and ends by calling add (Statics.re:204-269). add works out the error marks, the inspector's message and the fixed type, builds the record, writes it at every id of the term, and returns the same elaboration it wrote (Statics.re:268). So the walk has two outputs at once: the map, and the root's elaboration, which Statics.mk returns for the evaluator (Statics.re:4350-4381).

Two more facts about the map matter for #2651. Some passes throw their map away: probes such as the let's recursion probe (Statics.re:2070) analyze a whole subterm and keep only its type. And statics already reads its own map back in the middle of the walk: the let's fixpoint patch (Statics.re:2216-2228), the ModuleExp case's class override (Statics.re:2743-2756), and a module's type, built from the records of its exported patterns (ModuleHelpers.re:413-439). #2651 adds one more read of the same kind.

One record: mode and self, context in, co-context out

Hazel's statics has long been described in terms of a mode (analyze against a type, or synthesize one) and a self (what a term gives, errors included), and both used to be types of their own; Matt Keenan removed them (d22a778d64, Mode, 2025; ae3f3edde3, Self, 2026). Today the mode is just the expected type, ana: Unknown(SynSwitch) means synthesize (StaticsBase.re:263). The self is the synthesized type, elab_syn_ty, with the marks and message add computes, and ty is their meet with the expected type (StaticsBase.re:268-277).

The context goes down: a list of entries, newest first (Ctx.re:37-57). A variable looks itself up there and reports itself unbound if it is missing (Statics.re:691-705). The co-context goes up: each free variable with the ids of its uses (CoCtx.re:30-53). A binder takes its own names out (CoCtx.re:43-53), which is how unused variables are found, how a let decides it needs a fixpoint, and how a probe knows which bindings to capture (StaticsBase.re:46-53).

Elaboration inside statics

There is no separate elaborator. Matt Keenan's cc620bbbdc ("delete elaborator", committed 2026-04-17) folded it into statics: each case builds its node's elaboration from its children's, and add records it. One detail of that port is the subject of #2651. The old elaborator elaborated a module binding's definition by reading the info map, with no second analysis (Elaborator.re:518-524a81e3188fd); the port turned that into a second call to the walk, def_elab_direct (Statics.re:2757-2762). #2651 returns to reading the map.

How a let is analyzed

A let analyzes its definition more than once (Statics.re:2023-2248). It first types its pattern, then runs a recursion probe: a full analysis of the definition in the pattern's context, map thrown away (Statics.re:2070). Whether the let is recursive is decided by shape alone: one bound variable and one function of arrow-like type (Statics.re:2024-2039, Statics.re:2076). If not, one real pass analyzes the definition in the outer context (Statics.re:2079). If so, two more passes are thrown away and a final one runs with the name in scope (Statics.re:2090-2122). The body follows, then the pattern again with the body's co-context, for unused-variable warnings (Statics.re:2152-2155). Last, the let builds its elaboration: the definition aligned to the pattern's labels and given the function's name, or, when the definition uses its own name, wrapped in a fixpoint, FixF (Statics.re:2172-2230).

So on dev every let analyzes a definition that is not a function twice, and a function four times, and these multiply with nesting. #2603 (a let is analyzed once unless it refers to itself), open, skips the probe for a definition that is not a function, and keeps the probe as the final analysis for a function that neither uses nor shadows its own name (Statics.re:2070-20892603 head, Statics.re:2113-21622603 head).

Modules: a module binding is a let

On dev a module is "a syntactic gloss over labeled tuples" (modules.md:5). A module literal { … } is lowered to a chain of lets and type aliases ending in a labeled tuple of its exported names (ModuleHelpers.re:286-337, ModuleHelpers.re:162-171) and analyzed as that (Statics.re:2693-2724). A signature is a type that desugar_sig turns into a labeled product, dropping its type items (Typ.re:615-657). Andrew Blinn built this module system and the module keyword in February 2026 (b0735de6d6 to 131f508825).

module M = def in body, step by step

module M = def in body is a ModuleExp, and it has no typing rule of its own. Its case on dev (Statics.re:2725-2772) does seven things, Figure 8:

  1. Records the name's cursor info, an InfoMPat (Statics.re:2728-2735).
  2. Turns the name pattern into an ordinary pattern, desugaring a signature annotation to a labeled product (ModuleHelpers.re:51-60).
  3. Builds Let(pat, def, body) and gives it the ModuleExp's own id (Statics.re:2736-2741).
  4. Analyzes that let (Statics.re:2742): the probe and real pass over def, the body, and the pattern, whose record overwrites the name's InfoMPat.
  5. Changes the class in the let's record to ModuleExp (Statics.re:2743-2756), which step 7 overwrites anyway.
  6. Analyzes def again, directly, against the signature or nothing, to get def_elab_direct (Statics.re:2757-2762). This pass's records overwrite the let's for every node inside def.
  7. Builds the binding's elaboration with moduleexp_elab and adds the ModuleExp's record (Statics.re:2763-2772).

What moduleexp_elab builds, and what it drops

moduleexp_elab takes the let's elaboration and swaps its definition for def_elab_direct, and strips the signature from the pattern (ModuleHelpers.re:447-456, ModuleHelpers.re:364-371). That drops everything the let put around the definition: the label alignment, the function's name (Exp.re:544-551) and a fixpoint. The alignment is the one that matters on dev. Against a one-member signature, alignment would wrap a module's let-chain as (x = whole module) (LabeledTupleHelpers.re:49-75), and dev's test module M : { let x : Int } = { let x = 42 } in M.x gives 42 only because of the swap (Test_Evaluator_Modules.re:123-129). Stripping the signature means a module is not sealed at run time on dev: its value keeps every member.

How members enter the context

The name enters the body's context twice (Figure 10). As a value, the pattern binds a variable whose type is the module's labeled product (Statics.re:3164-3193). As a type, the let adds an alias under the module's name for its type members (Statics.re:2124-2151). A capitalized M parses as a constructor, and the Constructor case turns it into the variable when a variable is its newest binding (Statics.re:1561-1597). M.x is then a labeled-tuple projection (Statics.re:1278-1420; at run time Transition.re:1024-1058), and M.T a type projection through the alias (Typ.re:481-500).

The second commit: a definition that names its own module

The first commit lost an error. module F = fun x -> F(x) in 1 is one variable bound to one function, so the let takes its recursive path and analyzes the definition with F in scope: no error. On dev the direct pass then analyzed it again in the outer context, where F is not a variable, and marked it a free constructor (Statics.re:1598-1606, ConstructorStaticsHelpers.re:61-64), overwriting the let's records. With the read-back, nothing overwrote them, so the error was gone; the correctness review in ^report(21) found it by running both commits.

29c08fd8fa adds names_itself: if the let's elaboration is Let(_, FixF(_), _), the let saw the definition use its own name, and the direct pass runs as before (Statics.re:2764-2774PR). The fixpoint is the signal because the let removes the name from the co-context of the definition's record (Statics.re:2216-2228), so the record itself cannot show the self-reference. A test pins the error (Test_Statics_Modules.re:406-413PR).

Run with the command-line tool, the program reports "Constructor is not defined" at the inner F (1:21) and runs to 1, at dev and at 29c08fd8fa alike; so does the same definition under a signature, module F : Int -> Int = fun x -> F(x) in 1 (at 1:34), which takes the fallback's other arm (the runs).

Found in review: the guard also matches a fixpoint the user wrote. Alexander found on #2651 (his comment) that module m = fix f -> fun x -> … f(x - 1) in m(3) elaborates to Let(_, FixF(…), _) too, because fix itself elaborates to a FixF. So the read-back is skipped and the definition is analyzed a third time, after the let's recursion probe and its own pass. On Modules II part 1 with #2651 merged, a temporary print in that match fired for every module … = fix … he tried (four programs), and not for a fix inside a module body. The results match dev, and only the speed-up is lost, but the check does not test what names_itself claims to. Telling the two apart by shape is hard: skipping whenever the definition is a fix would also skip module m = fix g -> fun x -> … m(x - 1), which, as he read it, gets its unbound-m error from the fallback. (Building the follow-up found that on #2651 the let's own analysis already reports that m as unbound: a FixF has no function count, since Exp.get_num_of_functions returns None for it, so the let is not recursive there, and the fallback then reports the same mark again, at the same id. With names_itself made to skip a fix, the error is still reported; what the skip keeps is the recursion probe, two analyses per module instead of one.) So, he concludes, the signal belongs in the let analysis itself: an argument that makes a module binding non-recursive (his suggestion in question 3), with no shape check and no fallback, and fix still the way a module binds a recursive function.
