What a Call into Hazel Costs

Matthew asked, on 2026-10-22, about ^ticket(531), the experiment that moves Messed Up Dress Up's room rules into Hazel modules run through Hazel's JS library (#2719, the library; the game's side is the draft matthewhammer/kids-choice-games#2): why is Hazel so slow here for 16 x 16 map? do more analysis please, and draft a new report. The World room's rule takes a step on the map; in the game's own node run it costs 40.0 ms p50 at 16x16, against 0.003 ms for the same rule in JS. This report takes that one call apart.

Which build. Hazel's JS library, hazel-lib.js, from #2719 (branch js-library-embed at 0d66c36618), which is #2719 on #2711 on dev at 962a7cb009. Of the 14 performance PRs on the dashboard it has one, #2679, the only one merged into dev; the other 13 are open. Matthew, after the first draft: Let's make it clear what branch we are measuring ... how many have been applied? If they are not all applied, how much would they help? So every time below is measured three ways, on GitHub's builds of three branches: before, that build; + #2681, with #2681 merged (it carries #2661); and after, with all 14 (Before and after the performance PRs).

Short answers. All times are node on the Ubuntu laptop, p50 of one call with the target cell mid-map, the mean of two interleaved rounds; before is the measured build (1 of 14 PRs), after the same with all 14.

  1. Most of the time is a type annotation in the rule, and #2681 removes it: 144 ms becomes 20.6 ms at 16x16, 7.0x faster, with the rule unchanged. The rule's recursive helper is written fun (cs, c, r) : ([Cell], Int, Int) ->. Before, Hazel checks that ascription at run time on every call, by walking the value, so each step of the walk re-checks the rest of the list: one linear walk becomes a quadratic one (678 ms at 24x24, against 40.8 ms without the annotation). #2681 remembers which values are known to have a type, so the re-check is one lookup: 42.8 ms at 24x24, the same as the unannotated rule.

  2. Every call pays a floor that grows with the map, and the PRs raise it by about a quarter: 8.54 ms at 16x16 before, 10.6 after (19.3 and 25.3 at 24x24). Hazel's call boundary turns the whole JS argument into unevaluated Hazel syntax, gives every node a fresh id, and then evaluates it back into the value it already was, node by node; the (Globals, Event) parameter type walks it again. A rule that does nothing still pays this. No PR touches the library's conversion (of_js) or its fresh ids. And the argument is a new value on every call, so #2681 has never seen it: its first push walks it as before and also records every part in the memo. The rise is already there with #2681 alone (10.1 ms), and it repeats in both rounds.

  3. Underneath, each evaluation step costs about 3 µs, so even the plain walk is 25-80 µs per cell. A countdown over plain Ints costs 3.836 ms for 128 steps before, 3.162 after (one round each: 18% less, not far past this laptop's noise). The time is spread over the evaluator's per-step pipeline, jsoo's generic calls, fresh ids and GC; there is no single hot spot, and none of the 14 PRs aims at it.

  4. Passing only the neighbouring cells makes the call flat: 0.889 ms at 16x16, 0.782 ms at 3x3. That is the one change, available today without touching Hazel, that removes the dependence on map size: 162x faster than the shipped rule at 16x16 before the PRs, and still 23x after them, with the same answer.

  5. The 14 PRs together halve the compile: the game's rules compile in 402 ms after, against 797 ms before. That is once per program, at load. Per call, everything they change is #2681's: the bars of Figure 3 for + #2681 and after agree within noise. Eight of the 14 cannot reach a library call at all; they speed up the editor, its worker and its recovering parser (the table).

What happens in one call

The game compiles each room's module once (runProgram) and keeps the JS function Hazel gives back for the room's on_event. On each event it calls that function with two arguments, Globals and Event. For the World room, Globals holds the player's position, the map size and cells, a list with one record per square: {col, row, kind, ways}. The game rebuilds it on every event (0.098 ms in JS at 16x16, negligible). Inside the library (src/web/HazelLibCore.re, function_of), each call then:

  1. runs of_js on each argument. This does not build Hazel values: arrays become ListLit syntax, objects a Tuple of TupLabels, and every node gets a fresh id (Exp.fresh, which calls Id.mk, a UUID). 256 cells make about 4.6k nodes.
  2. builds Ap(f, arg) and evaluates it from scratch, with no statics and no reuse.
  3. the evaluator steps the argument back into a value, one node at a time, through the whole stepping pipeline (Transition.re's ListLit, Tuple and TupLabel cases).
  4. matching the parameter pattern (g : Globals, e : Event) pushes the type ascription through the whole record (Ascriptions.re), allocating a fresh Asc node and id per element even where nothing changes.
  5. runs the rule, then converts the (small) result back with to_js.

A 16x16 call with an event the rule ignores (| _ => Done) costs 13.8 ms; the same call with no cells costs 0.44 ms. That difference is steps 1, 3 and 4 alone, about 3 µs per node. Its profile shares are in Figure 2; Id.mk is about 20% of all time, and the top self-time entry is caml_subarray_to_jsbytes, the byte copy in its UUID.

Why the rule's walk is quadratic

The World rule finds the target square with a recursive helper:

let find = fun (cs, c, r) : ([Cell], Int, Int) ->
  case cs | [] => ... | x :: rest => if x.col == c && x.row == r then ... else find(rest, c, r) end

Hazel's evaluator treats a pattern with a type ascription as a run-time check: PatternMatch.re wraps the argument in Asc(d, ty) and Ascriptions.transition_multiple pushes it through the value, element by element and field by field. So find(rest, c, r) re-checks all of rest, at every step. A walk to index i in a list of length L costs about i × L. In a profile of a deep find, 58.6% of the time is in transition_multiple under matches_inner.

That is also why the game's own figure, 40 ms, is lower than this report's 144 ms: the cost depends on where the target sits in the list. With all four ways set, a target at index 1 costs 18 ms at 16x16 and the last one 244 ms; removing only the annotation brings the last to 33 ms (8x8: 23 to 8.9 ms). The Square room's find and doors helpers are annotated the same way, which fits a lever with 40 doors taking about 85 ms.

What would fix it

In the game's rules, available today

  1. Drop type annotations on recursive helpers (World's find, Square's find and doors): 144 to 18 ms at 16x16 on the measured build; linear instead of quadratic. Not needed once #2681 is in, which gives the same without touching the rules.
  2. Pass only what the rule needs: the neighbouring cells, not the map. Flat at about 0.9 ms at every size. All 17 Globals fields go to every room today, and each is converted and re-stepped per call.

In Hazel's library and evaluator

  1. Do not re-step a converted value. Have of_js produce something the evaluator treats as final (or bind the argument in the environment and apply to a variable). About half the floor.
  2. An ascription fast path: this is #2681, measured above. It remembers which values are known to have a type, so the recursive find(rest, ...) re-check is one lookup: the annotated rule becomes linear without changing it (144 to 20.6 ms at 16x16). It is open, on top of #2661. What it does not do is cheapen a value's first push, which it now makes about a quarter dearer by recording it; checking a fresh value without allocating would.
  3. A cheaper Id.mk, without Uuidm.v4's byte copy under js_of_ocaml: about a fifth of all time.
  4. Cut the per-step pipeline when nothing uses it: the state merge, reuse check and probe sampling run on every step even with no probes and no reuse (8.1%, 8.0% and 6.8% inclusive in the walk's profile).

Fix 2 already brings the shipped rule onto the unannotated one, on its branch. Fix 1 would take the floor to perhaps a third of today's, and with it the first-push cost #2681 adds; fix 4 is what would make a linear walk cheaper. None of them makes Hazel's walk cost what JS's does (under 1 µs); a rule's design still decides whether the call depends on the map's size.

What next

  1. Change the World and Square rules on matthewhammer/kids-choice-games#2: no annotations on recursive helpers, and neighbours only in World's Globals; re-time the game's moves at 16x16.
  2. Land #2661 and #2681 in dev, then rebase #2711 and #2719 on it: the game gets the linear rule without changing its rules. (Measured here on trial/r25-2681.)
  3. Prototype of_js producing final values, and time the identity rule's floor; it would also remove the first-push cost #2681 adds.
  4. Pin the noise floor: two rounds give a spread under 20% for nine in ten of the times; five would say more.
  5. Measure the compile's halving PR by PR (#2603, #2651, #2608).

How this was put together

Node v22.23.2 on the Ubuntu laptop (Intel i7), one process at a time. The library is hazel-lib.js from #2719 at 0d66c36618: the minified build for every time, the dev build hazelLib.bc.js for named profiles (3 s each). The rules are the game's at 2ebda59ab4. Each time is one p50 over 20-60 reps after warm-up; for that first run the noise floor was not measured, so treat differences under about 10% as noise (the reruns below give it: under 20% for nine in ten times). The target cell is mid-map, at (n/2-1, n/2), moving east; every variant's result was checked against the game's World handler. The library exposes no step count, so per-step costs are inferred from timings. The drivers are in drivers/ (r25.mjs for the sizes, steps.mjs, profheld.mjs, and the earlier prof.mjs and prof_noann.mjs; they read the game and library from local checkouts); the data is in data/, and the profiles, too big to keep, are summarized in data/profiles.json.

Before and after the PRs: drivers/prs.sh runs r25.mjs on GitHub's Deploy builds of three branches (hazelgrove/build, <branch>/hazel-lib.js): js-library-embed at 0d66c36618, trial/r25-2681 at 9e461fcc09 and trial/r25-all-perf at 8756a15dfc, in two rounds with the builds interleaved (before, + #2681, after; then again), one node process at a time, pinned to two threads and niced, as this laptop needs. Every time above is the mean of the two rounds; each round is in data/prs/, with each build's compile times. The builds and the 14 PRs are in data/prs.json. The per-step costs are one round per build (steps.mjs). The figures and the first table use these reruns; the first run is the first draft's, kept as it was.
