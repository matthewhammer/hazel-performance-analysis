Hazel reports · ^report(21) · 2026-10-19 · work in progress

Of 19 performance PRs, 16 keep types and values the same; two change a result in a corner, and one is a spike

Cyrus asked whether the performance PRs compromise the correctness of typing or evaluation, and for more analysis and coverage of functional correctness. For each of the 19 PRs against #2609 (the performance tracking issue), this report says what it caches, skips or shares; why the result is the same as without it, or where it is not; what that rests on; and which tests back it and which are missing. For the meeting with Cyrus on 2026-10-21.

Short answers. As of 2026-10-19, each PR read at its head (commit ids below). Two corners were confirmed by running the PR against its parent; the rest is from reading the code.

  1. 16 of the 19 keep every type and value the same. 4 are tests and budgets that cannot change a result; 5 hold outright; 7 hold under an assumption stated with each (below).
  2. 2 change a result in a corner, both confirmed by running. #2610's load fallback, when it splits a long program just after an operand, loads x - y as x ¿ - y: a new hole, and the minus turned unary, saved back on the next edit. #2651 changes what a module under a one-member signature evaluates to (an ill-typed program, and the new value looks like the right one), and drops an error for a module that names itself.
  3. 1 is a spike, not for merging: #2490 (the evaluator compiled to WebAssembly) removes the builtin livelits to build. It is a draft and says so.
  4. The assumptions worth naming: three PRs treat a structural hash as equality (#2661 and #2681 a 60-bit type hash, #2673 a 64-bit term hash), so a collision would silently give a wrong answer; #2673's hash has a structure that makes some collisions easier than chance. #2606 relies on every finished incremental cache being consistent. All rely on terms never being mutated in place.
  5. The biggest gap is in the tests, not the PRs. The property that compares incremental evaluation with evaluation from scratch is switched off on dev (#2457), and no test runs a program with an optimization on and off and compares. A tests PR to dev can add both (below).

#2603: Statics: a let is analyzed once unless it refers to itself, plus three smaller speedups Same results, under a stated assumption

Read at 70e6677bdb

What it changes. A let whose definition is a function that neither mentions its own names nor shadows an outer one is analyzed once (the recursion probe's analysis becomes the final one), and a non-function definition skips the probe; context lookups answer the builtins from a hash table; meet is computed once per node; completion skips variables that cannot match the typed token.

Mechanism. Reuse when the definition is function-shaped, shadows nothing, and its analysis read none of the pattern's names (CoCtx.has_any); the builtin index is keyed by the physical identity of the builtin list; the shared meet answer is used only when all three old calls were literally the same call.

Why the result is the same. The probe's inputs are exactly those of the old recursive path's first pass, and statics is pure apart from fresh-name counters. With no shadowing, every other name resolves the same way in both contexts, and every way of looking up the binder is recorded in the names the definition reads; so when none of them was read, the final pass would equal the probe. For a non-function definition the old probe only fed a recursion test whose first case already answered false.

What it assumes. That a definition depends on the context only through lookups recorded in the names it reads, and that statics is pure.

Where it is weakest. One corner: a derivation quote (DrvQuote) looks names up but records none, so a quote that names the let's own binder is invisible to the reuse check, and an error mark (VarNoJoin) that the old final pass reported goes missing. Elaboration is unchanged. Very unlikely. Not checked: whether Typ.equal can tell two analyses apart through fresh variable names under Poly.

Tests that back it:

  • Statics.Let: three type checks (plain, recursive, shadowing) and a timing test of 12 nested lets.
  • Ctx.TailIndex compares the indexed lookup with a plain scan; TyDi.PrefixPruning.
  • The PR reports identical analyze -W output on 72 programs (errors and warnings only).

Tests to add:

  • The old let behind a flag, compared per id (type, marks, names read, elaboration) and by evaluation, over the corpus and random nests of lets.
  • Cases: let (f, g) = … where only g calls f; an annotation that disagrees (let f : Int = fun x -> x); definitions with holes; a derivation quote naming the binder (which would fail today).

#2651: Statics: a module binding analyzes its definition once, not twice The argument does not hold

Read at e3013b0360 · since fixed at 29c08fd8fa: the self-naming error is back, and the one-member corner is kept, with a test for each

What it changes. A module binding reads its definition's elaboration back from the info that the expanded let already wrote, instead of analyzing the definition a second time (kept as a fallback).

Mechanism. The elaboration is read at the definition's representative id in the current run's info map.

Why the result is the same. When the let's last analysis had the same context and expected type as the direct call, and recorded exactly the elaboration it returned, and took the non-recursive path, purity gives the same elaboration. A definition that is not a function is never recursive, so that holds in the normal case.

What it assumes. That the let's recorded elaboration equals what a direct analysis returns, and that the definition is not recursive.

Where it is weakest. Singleton-signature lifting: when a module is ascribed a one-member signature and has more members (module M : { let x : Int } = { let x = 1; let y = 2 } in M.x, an error on dev that still runs), the lifting path records a different elaboration from the one it returns, so M at runtime is now the module's own elaboration instead of the label wrapper: evaluation changes (arguably for the better, but not "the same output"). A function definition naming its own module (module F = fun x -> F(x), parser not checked): the read-back elaboration has F unbound with no error mark, where the old second pass reported a free-constructor error. Confirmed by running the first corner with the command-line evaluator at #2651's head (e3013b0360) and its parent (34f9605ddf, dev): M evaluates to (x=({ let x = 1; let y = 2 })) on dev and to (x=1, y=2) with #2651, and M.x to { let x = 1; let y = 2 } on dev and to 1 with #2651. The new results look like the right ones; dev already reports this program as a type error. The second corner, confirmed by running too: for module F = fun x -> F(x) in 1, dev reports a static error at F inside the definition, and #2651 reports none (both evaluate to 1, as F is not called).

Tests that back it:

  • None added; the PR reports the Module, Statics, Elaboration and Evaluator groups passing (913 tests). The evaluator's module tests never reach the lifting path.

Tests to add:

  • Evaluation tests for both corners.
  • Old against new elaborations over every program with a module.
  • A dev-build assertion that the read-back elaboration equals the direct one.

#2661: Types get a Merkle hash; the evaluator asks is_consistent once per pair Same results, under a stated assumption

Read at 0875dfcd66

What it changes. Types get a structural hash that ignores ids and the provenance of unknown types, cached per object; the evaluator's consistency check when pushing an ascription through a constructor application is remembered per pair of hashes.

Mechanism. A global table from a pair of 60-bit hashes to a boolean, emptied at 4,096 entries, caching is_consistent(Ctx.empty, unroll(sumt), unroll(t)). Types with expressions inside (proofs), projectors and signatures get no hash and are never cached.

Why the result is the same. The answer depends only on the two types' structure, not on ids or on unknown types' provenance: every unknown case succeeds whatever its provenance, variables in an empty context compare names, and bad sum entries cannot change the result. The hash covers every constructor and field except ids and provenance; binder names and constructor order are included, which only costs missed hits.

What it assumes. That equal 60-bit hashes mean structurally equal types, and that types are immutable.

Where it is weakest. The hash is not cryptographic (a base-31 polynomial and an FNV-like lane, each mod 2^30, and for atoms the second lane is an affine function of the first). A collision would give a wrong consistency answer: a mismatched constructor application pushed through, or a consistent one cast. Rare, no adversary, but silent.

Tests that back it:

  • TypHash: 10 tests of the hash's properties.

Tests to add:

  • A property test over random type pairs (random ids, provenance, parens, recursive types, bad entries): the remembered answer equals the direct one, in both orders.
  • A census over every type in the corpus's info maps: same hash implies equal up to ids and provenance.
  • The evaluator with the memo on and off, compared.

#2679: An ascription pushed through a value gives the value back when it already has the type Same results: the argument holds

Read at c82726a3c2

What it changes. Pushing an ascription through a list, cons, tuple, label or constructor payload returns the value itself when every part comes back unchanged, instead of a fresh copy.

Mechanism. Physical equality on the children; only a recursive push can return a child unchanged.

Why the result is the same. Every place the push returns its input unchanged (an unknown type, a matching atom, a consistent constructor, and the new cases) returns exactly its input, so when every child comes back as itself, the rebuilt node equals the value.

What it assumes. That values are immutable, and that nothing depends on the old copy's stripped annotations.

Where it is weakest. Values now keep their source annotations past an ascription (all their ids, comments, incomplete marks), where the copy had stripped them: the stepper or result printing could show a comment inside a value, and id-keyed machinery sees all ids. Display and metadata only; no bug found.

Tests that back it:

  • Test_Ascriptions: a well-typed list of labelled tuples keeps its identity; a list holding a function is still wrapped.

Tests to add:

  • Old against new over a corpus: results equal, step counts and stepper traces identical.
  • A property test over random typed values.

#2681: A value known to have a type is not walked again for it Same results, under a stated assumption

Read at 8546bde64e · its branch also merges #2661 and #2679

What it changes. The evaluator remembers, per value (a term block, or a list's cell), the type hashes at which pushing an ascription returned it unchanged, and skips the walk the next time; a list records every tail.

Mechanism. A weak map keyed by the value's physical identity, holding type hashes (from #2661). Values are immutable, so nothing needs invalidating; dead keys are dropped.

Why the result is the same. The push decides only from the term's contents and the type (ids are used only to build copies), so two values sharing a term behave the same. A list can come back as itself only when every element did, at an unknown type, or through parens forwarding to one of those, and in each case every suffix list at the same type also comes back unchanged (so recording tails is sound). Values that need wrapping (functions) never come back as themselves, so they are never recorded.

What it assumes. #2661's no-collision assumption; that terms and lists are never mutated in place.

Where it is weakest. A collision would hide a failing push: a list remembered at [Int] would pass unchanged at a type with the same hash, skipping the cast failure. Same probability as #2661.

Tests that back it:

  • Test_Ascriptions: a list's tails are remembered, only for that type; a value without the type is not remembered (mutation-checked on #2635, the PR says).

Tests to add:

  • The memo on and off over a corpus and random programs with annotated parameters: results, step counts and cast errors compared.
  • A wrongly typed head consed onto a remembered tail.
  • A fake hash injected to force a collision, showing it is the only way to a wrong answer.

#2606: Keep the incremental cache in the eval worker Same results, under a stated assumption

Read at 1b5de419b3

What it changes. The eval worker keeps the last finished incremental cache for each (document, key), at most 32 slots, and answers without sending the cache back; a request asks for the held one instead of sending its own.

Mechanism. WorkerServer.Held, keyed by (document, key). A failed run (a step-limit timeout included) drops its slot, a superseded run is never kept, a restarted worker starts empty, a 33rd slot clears the table. The held cache is swapped in once per request, before both the reuse plan and the evaluation run.

Why the result is the same. The reuse check never trusts where its earlier cache came from: for each node it re-checks the elaboration, the provenance of every name the node reads, and the probe targets against the new request. So a cache from an earlier run, or from another program that shares ids, is reused at a node only when the node and all it reads are the same, down to the builtins.

What it assumes. That every finished cache is internally consistent: each entry's value was computed from the values its sources hold. That holds by induction over runs, with one gap shared by all incremental reuse: whether a source counts as reused comes from the reuse plan's prediction, not from what the evaluator did.

Where it is weakest. A bad cache, if one ever exists (the #2457 kind), now survives slide resets and undo until the worker restarts or the page reloads. Some documents share a slot (slides of the same name; three modes send an empty document name), which costs reuse, not correctness. The tests skip the worker's real request path, and their program is below the size where the worker uses an earlier cache at all.

Tests that back it:

  • A new group, WorkerServer held cache (4 tests): a slot is kept and left out of the answer; documents and keys are separate; an edited program run against the held cache equals a fresh run; a failure drops the slot.

Tests to add:

  • Across programs: for programs A and B from the slides and the tutorial, evaluating B with A's cache equals evaluating B fresh (value, probes, test results).
  • The same through the worker's yielding path, with a superseding request mid-run, on a program above the incremental threshold.
  • An edit sequence replayed three ways (held cache, the page's cache, fresh), compared at every step.

#2608: Leave the source's whitespace and comments out of elaborations Same results: the argument holds

Read at 66f789d916

What it changes. Statics builds elaborated expressions and patterns without the whitespace and comments (secondary) around each source node, which only made elaborations bigger.

Where it is weakest. A future reader (say, quotation that keeps formatting) would silently get none. The stripping is incomplete (labelled-tuple wrappers, the nodes of types inside an elaboration), which costs size only.

#2673: Incremental evaluation recognizes an unchanged expression by its Merkle hash Same results, under a stated assumption

Read at cea8f0a98f

What it changes. The reuse check first asks whether the cached and new elaborations hash the same (a structural 64-bit hash of the runtime value, remembered per object); if not, one structural walk compares the terms and their lexemes together, remembering each answer per pair of objects.

Mechanism. Util.ValueHash over the whole value (ids, lexemes, whitespace); memos never invalidated, relying on terms never being mutated; values with functions, unforced lazies or cycles get no hash and fall back to the walk. The shortcut is used only with alpha-equivalence off and no environments, so identical subterms mean the same thing.

Why the result is the same. Equal hashes mean an identical structure (barring collisions), and on identical structures the old check was true too. Where the new walk differs: stricter, a parenthesized literal against a parenthesized literal under new ids, or a slider over an Int literal, compares unequal (lost reuse, never wrong); laxer, (e) against e compares equal where the old check refused, and both evaluate to the same value (parens and projectors take one side-effect-free step), though a replayed step count can differ by the number of wrappers.

What it assumes. That the 64-bit hash never collides, and that terms are never mutated in place.

Where it is weakest. A collision silently reuses a wrong value. The hash has a structure that makes collisions easier than chance: each lane is an xor-multiply chain in which flipping bit 31 of a child flips only bit 31 of the state, so two children both differing exactly in bit 31 cancel. Elaborations have few raw int fields and no realistic colliding term was found, but a finalizer per lane (or a 128-bit hash) would remove the structure. The PR claims the same reuse decisions as before; that is not quite so.

Tests that back it:

  • ValueHash (5 tests), one_walk_lexemes_test and lexeme_edit_test in the incremental suite.

Tests to add:

  • A QCheck property over random terms and random edits (new ids, lexeme and literal edits, parens and projectors added or removed, a binder renamed): the hashed check equals the old one, and equal hashes imply equal terms. It would catch the parens case.
  • Old against new reuse decisions at every node of the slides and the tutorial, after an edit and after replacing all ids.
  • No two structurally different subterms of that corpus share a hash.

#2675: Incremental evaluation reuses expressions around a recursive let Same results: the argument holds

Read at 1e5207494a

What it changes. For a recursive let, statics' record of the names the definition reads (its co_ctx) now leaves out the let's own names, which the fixpoint binds, so an edit elsewhere no longer forces the recursive definition and everything after it to re-run.

Mechanism. The co_ctx decides which names the reuse check must find unchanged; removing a name removes a dependency.

Why the result is the same. A recursive let elaborates to Let(p, FixF(p, def), body), and its definition was analyzed with the pattern's names in scope, so every use of those names in it refers to the recursive binding the fixpoint binds. The free variables of FixF(p, def) are exactly the definition's minus the pattern's names, which is what the new co_ctx computes; a non-recursive let x = x + 1 still reads the outer x.

What it assumes. That the fixpoint binds exactly the names the pattern adds to the context (the fixpoint's own node already assumed this).

Where it is weakest. It widens reuse in exactly the programs (modules of recursive helpers) where any gap in cache consistency would show, while the property that compares incremental with fresh evaluation is switched off on dev (#2457).

Tests that back it:

  • Two new cases check the result and the reuse plan after an unrelated literal edit.

Tests to add:

  • Incremental against fresh after editing an outer variable used inside the recursive definition (let k = 7 in let go = fun i -> if i == 0 then k else go(i - 1) in go(3): editing k must not reuse go), mutual recursion, function sugar, and an outer binding the recursive name shadows.
  • Re-enable the incremental-against-fresh property, with a generator that makes recursive lets.

#2610: Parse the load fallback with the segmented parser, projectors kept The argument does not hold

Read at 0aba66119a · since fixed at 94ca8a2daa: the joined pieces are remolded once, with three split tests

What it changes. When the fast parser rejects saved text, the fallback now types it in as top-level pieces of at least 100 characters, each into a fresh zipper, joined and re-grouted once, instead of character by character; projector pins are kept.

Mechanism. Parser.to_zipper_segmented splits where the caret is at top level, outside any token, with no missing shards, just after whitespace (Parser.re:81-85). The join is re-grouted (Parser.re:158), never remolded, and the caller does not remold afterwards.

Why the result is the same. The PR checks the printed text against the character-by-character parser on 128 inputs, and keeps projector ids across the split (sound).

What it assumes. That a piece's first token is molded the same way without what precedes it. That is false for tokens whose mold depends on their left neighbour.

Where it is weakest. - (binary or unary) and ( (application or parentheses) are molded by their left neighbour, and an ascription's right side switches to types. If a split lands just after an operand, as when 100 characters end inside x in a top-level x - y, the next piece starts in a concave context: - becomes unary minus and the join gets a hole, so aaa…a - b loads as aaa…a ¿ -b, and f (b) as f ¿ (b). Splits also happen right after a comment's closing #. Rare per program, but silent at load, and written back on the next save. Confirmed by running Hazel's format at #2610's head (0aba66119a) and its parent, on a program the fast parser rejects (a concave hole earlier on) followed by a 100-letter name and - b: the parent loads aaa…a - b, #2610 loads aaa…a ¿ - b. (Both turn c ¿ d into c ¿ ¿ ¿ d; that is older than #2610.)

Tests that back it:

  • Parser.Segmented compares 5 files and a prose paragraph with the character-by-character parser, by printed text.

Tests to add:

  • The confirmed case (a forced fallback, a top-level x - y with the split inside x), and f (y) and e : T at a split, against the character-by-character parser.
  • A sweep of split positions: each corpus program with 0 to 99 characters of padding in front, so every top-level space becomes a split point at some offset.
  • Fallback-shaped inputs (an unfinished form at the end, concave holes), compared as terms, not only printed text.
  • A likely fix, not yet tried: remold the joined zipper once before the final re-grout.

#2614: Load text about 2.5× faster: whole tokens, one re-grout Same results, under a stated assumption

Read at b4e3914b03

What it changes. Loading types each run of operand or operator characters in as one insertion and re-grouts once at the end, not after every character; rescanning returns its own argument when nothing changed, tested by identity; a carriage return reads as a newline.

Mechanism. to_zipper ~by_run; take_run stops where typing would stop extending a token; one remold_regrout at the end; Siblings.rescan returns its argument unchanged when nothing converted.

Why the result is the same. The identity check is exactly the old structural one: rescanning alters a piece only at a conversion, which it flags. Whole-token runs: the operand and operator character classes are disjoint and no token spans both, and insertion still merges with its left neighbour. One re-grout: remolding skips grout and passes shapes through, so molds cannot depend on grout, and the final pass puts the same 0 or 1 grout at each junction.

What it assumes. That insertion's choices do not depend on grout or on per-prefix side effects (three places in Insert read grout, for ids, a suppressed space and the caret, none for the term).

Where it is weakest. A hole's place relative to a neighbouring space may differ (text and layout, not the term). A lone \r inside a string or comment now splits it into fragments (dev dropped it silently); rare and loud. CRLF text, which loaded with a hole on every line, now loads right. #2610 and #2614 both rewrite the same fallback: merging both needs a choice.

Tests that back it:

  • Parser.LoadPath (6 tests); 386 parse tests; a structural comparison on 72 programs, run once offline.

Tests to add:

  • In CI: whole-token runs on against off, ids erased, over the corpus and fallback-shaped inputs (prose, hole-heavy text, unfinished endings, x+-1, >>=, 1.5e-3, Unicode names, strings and comments with spaces).

#2652: Eval worker in Firefox: start it at load, and do not time out a reply that is queued Same results: the argument holds
