Hazel performance analysis · Issue 005 · 2026-10-12

Two threads, one picture: the worker, the page, and diffing the view

Hazel evaluates a program in a web worker and draws it on the page's main thread. A question from a meeting with Cyrus: how do our performance fixes so far compare with a more principled approach, where the worker builds a virtual DOM of each view, diffs it against the last one, and sends the page only the patches? Did we already do some of this, and how far does the idea go? Can a worker even build real DOM nodes? And is it expensive to keep several representations of the same DOM?

Short answers.

  1. A worker cannot build real DOM nodes. It has no document, and a DOM node cannot be posted from one thread to another. A worker can only build data, such as a virtual tree or a list of patches, for the main thread to apply.
  2. Hazel's worker builds no views today. It evaluates the program and sends back values. The page evaluates each livelit's view and turns the resulting Html value into a virtual DOM tree. The virtual DOM library diffs that tree against the last one and patches the page.
  3. What crosses between the threads is already incremental. Each side sends only the parts of a value the other side does not have yet, and a hash for the rest. This is a structural diff in all but name, and it cut a Kids' Choice release's messages from about 400 KB to about 16 KB.
  4. What is still done whole, on every change, is on the page: evaluating a changed view, converting all of its Html to virtual DOM, and the diff, which walks all of it. The principled version of the idea is to skip unchanged parts by their identity or hash, wherever the diff runs. On the page, that needs no new protocol, and it is the cheapest next step. Moving views into the worker would also take their evaluation off the main thread, but it would put a round trip between an interaction and its picture.

Update, later on 2026-10-12: measured, and C is not the next step. A profile of a figure move in the woods shows what the page does with its time. Converting Html to virtual DOM is 1.1% of it, and the diff and patch 0.9%. So C would save at most about 2%, while evaluating the view is about 69%. The next step is making the view cheaper, and moving it to the worker (B) after that. The numbers.

Who does what today

The main thread is the page: it owns the DOM, takes the user's input, and keeps the editor running smoothly. The worker evaluates the program, so that a long evaluation does not freeze the page. Here is one change, such as a slider's release, in order. The links are to the code on #2635 (livelits × modular editors) at b18cef1f5a.

  1. The page takes the edit, or a livelit's update, and runs statics, per item, on the main thread.
  2. The page builds a request: the elaborated program and what the worker needs of statics. Before posting it, it replaces each part the worker already holds with that part's hash (ShareCodec; hashes from ValueHash, a Merkle hash kept per object). Then it turns the request into a string with OCaml's Marshal and posts that.
  3. The worker reads the string and puts back the parts it kept.
  4. The worker evaluates, reusing its own cache of earlier results wherever an expression is unchanged, which it recognizes by hash. It sends back streams of partial results and then the result, trimmed and shared the same way: the page gets only what it does not have.
  5. The page reads the answer. Unchanged parts arrive as the very objects the page already holds.
  6. The page evaluates each livelit's view, if its definition or model changed: Hazel code, run by the page's own copy of the evaluator, giving an Html value (LivelitProj: memo_view, eval_view, live_html).
  7. The page converts the Html value to a virtual DOM tree (HazelDOM.go), whole, each time the view is drawn. Event handlers become OCaml functions here.
  8. The virtual DOM library (Jane Street's virtual_dom) diffs the new tree against the last one and patches the real DOM. Its walk skips a subtree only when the old and new are the same object. Below that, it compares tag, key and properties, node by node. Then the browser lays out and paints.

Can a worker build real DOM nodes?

No. A web worker runs JavaScript without a page. Its global scope has no window and no document, so there is nothing to create an element with and nowhere to attach one. Messages between threads carry only data: strings, numbers, plain objects and arrays, and a few kinds of buffer. A DOM node is none of those.

Hazel's code is built on this. The worker's program links only the language library (src/web/dune), and even calls setTimeout through the global object, since it has no window (WorkerServer.re). HazelDOM, which turns Html into virtual DOM, is in haz3lcore and is not in the worker at all.

A worker could build virtual DOM: the library is plain OCaml data, and the worker already links its types. But it could not send that tree to the page. A virtual DOM node holds its event handlers as functions, and a function cannot cross from the worker's program to the page's. What can cross is a description of the DOM whose handlers are data. Hazel has one already: an Html value is exactly that, a Hazel value whose handlers are Hazel expressions. So a worker-side diff would diff Html values and send patches to Html, and the page would still build the virtual DOM, or the DOM, from them.

Where a diff could go

Diffing two trees exactly is expensive in general: the best algorithms for the smallest edit between two trees take time cubic in their size. Virtual DOM libraries settle for something linear. They walk both trees together, keep a node when its tag and key match, and replace it otherwise. Hazel can do better than linear on the parts that did not change, because its values carry Merkle hashes and keep their identity when unchanged. An unchanged subtree can be recognized in one step and skipped. A diff then costs about the size of what changed, plus the path down to it, not the size of the tree. That is the principled version, and there are three places it could go.

Is it expensive to keep several representations?

A view exists in up to five forms at once: the Html value (in the view memo); in the worker's and the page's tables of shared values; the virtual DOM tree the page last drew, kept for the next diff; the new virtual DOM tree, during a diff; and the DOM itself.

In memory, sharing makes most of these cheap. The Html value and the tables hold references to the same objects, not copies: the boundary returns the page's own objects for anything unchanged. The two virtual DOM trees exist together only during a diff. The DOM is the only full copy that cannot be avoided. What memory these take has not been measured. The tables are capped at 200,000 entries each.

In time, the cost is rebuilding, not holding. Today, steps 7 and 8 rebuild a view's virtual DOM and walk all of it whenever the view is drawn. That is a cost per representation per change, and C is what removes it. On Kids' Choice it is small: converting the face's Html to the page took 8 ms of a 104 ms redraw (profiled, issue 001), and in an earlier profile, the browser's own layout and DOM work was about 30 ms of a 310 ms redraw. In the woods, with about 600 shapes, the conversion and the diff are part of the half of the page's time that is not evaluating the view (issue 004). How large a part has not been measured.

Update, later on 2026-10-12: measured: about 2% (below).

Counting the garbage collection it causes, evaluating the view is about 69% of the time. C can save only the two small rows, about 2%. It would also be harder than above assumed. The view's call memo misses on the woods' ~600 shapes, so each shape's Html is a new object on every change, even when nothing in it changed. A memo would need a content hash as its key, not identity. And each event handler holds the state it was drawn with, so a remembered node would need handlers that look the state up when the event fires.

So the order changes: first make the view cheaper to evaluate, per shape and in the evaluator's general overhead (done the same day, in three changes: the woods' redraw from a median of 2.20 s to 1.41 s, issue 004's update). Then consider moving it off the main thread (B), weighing the round trip it would add to each interaction. C waits. On Kids' Choice the conversion was 8 of 104 ms (issue 001), a larger share but a small time.
