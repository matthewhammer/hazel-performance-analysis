Proposed, in this order:

  1. Every cache has an off switch, and CI compares on against off. One differential harness over the slide corpus: types, marks, elaborations (ids aside), values, probes and test results, after random edits and from scratch, with each cache on and off. A performance PR registers its switch and gets the check. #2700's corpus test is its first case.
  2. The guards are tested too. For each cache, a deliberately wrong variant (a dependency ignored, a hash made to collide) must make the suite fail; run weekly, beside the extended tests. A guard that cannot fail guards nothing.
  3. Hash keys are checked for soundness. Equal hash implies equal term, for the type hash (#2661, #2681) and the term hash (#2673), with a census over the corpus.
  4. Every load path gives the same program. The fast loader, the recovering parser (#2610's segmented one), a saved slide's round trip and typing. ^report(21) found #2610's fallback turning x - y into x ¿ -y; ^ticket(472) is checking a saved Scenes slide whose livelit uses came back broken.

  6. The checks are required (the item on gating dev, below): Fast checks required for dev, after quarantining Evaluator.Properties.
  7. Each performance PR says what it caches, as ^report(21) writes each one up: the key, what invalidates it, what it assumes, and the test that fails if the invalidation is wrong.

12. Hazel tiles for a game's logic: Messed Up Dress Up as a Scratch-like world ideation, measured #12

Asked by Matthew, 2026-10-20 · ^ticket(473) · as of 2026-10-20 11:26

An idea, partly Matthew's to shape. Livelits show Hazel can express a great deal, but not yet fast enough to be a game's engine or its drawing. The game's logic is another matter, especially simple event declarations: when this happens in the game, queue that action, perhaps at once. Hazel tiles inside Messed Up Dress Up, customizing its behavior over its world, people and objects, would make each drive the other: more play, and more research. Such rules are small and run seldom next to the game's frames, so they fit Hazel's evaluator as it is.

Against Languages of Play (Martens and Hammer, 2017; HTML). The paper treats each game's interface as a programming language of player intent: its syntax the intents the game recognizes, its operational semantics the mechanics as inference rules for a step from a state and an intent to a new state and a response, its type system a contextual interface in which only what makes sense in the current state can be said; play traces are straight-line programs, and player skills general ones, with branching on the game's response, parameters typed by the resources they need, repetition and parallel composition, which it offers as a scripting language for modding and co-creative play.

  • Where they meet: "when this happens, queue that" is the paper's skill as a program, made reactive: a rule fires on a game event rather than being issued by the player, and its body is the same shape as the paper's do-then-case-on-the-response.
  • Where the paper goes further, and Hazel could follow: Dress Up's intents (walk, climb, sit, open, pull a lever, dress) as a typed syntax; the context (where the friend is, what is near) as the rules' type system, so a rule that can never apply is a type error rather than a silent no-op; the mechanics as inference rules, which Hazel can already hold as derivations, with the paper's "never gets stuck" as a property checked where the rules are written; play traces as structured values to query, as Hazel's probes already are.
  • What Hazel adds that the paper only anticipates (it cites Hazelnut): rules that are meaningful while half-written, with holes; the game's own controls inside a rule, as livelits (a slider for a jump's height, a picker for a place); and proof beside program in one editor.
  • Steps, smallest first: the events and intents as a Hazel sum type; rules as Hazel values the game reads into its queue; the context as types; traces the game logs as values Hazel can query; later, mechanics as inference rules.

Measured (^ticket(402), on #2635's code, the test build under node on a GitHub runner): a lever pulled flips every trapdoor a table of lever-to-trapdoor links names, written in plain Hazel, and again monadic (the rule returns commands as data, which a game would interpret against its globals, as Matthew asks: "we need global variables for simple games --- most scripts use them"). Statics and elaboration, once: 8 to 70 ms. Per pull: 0.7 ms with 10 links (0.95 ms monadic), 5.7 ms with 100, 65 ms with 1,000: linear in the table, since a list is scanned each pull. A trap room is a few links, so a twentieth of a 60-frames-a-second frame; drawing is what Hazel cannot do in time yet. The monad itself, $GameUpdate, with variables named by Fumola-like symbols, is ^ticket(479).

Sketched (^ticket(479)): the trap room's lever as a $GameUpdate program, a monad beside livelits' $UpdateCmd, its commands run by the game and each awaited (a walk takes time; the program resumes after), the game's variables named by typed, Fumola-like symbols:

# $GameUpdate: commands the game runs, each awaited, with do as for $UpdateCmd #
#   pure(a)          | get(@sym) / set(@sym, v)  the game's variables, by symbol #
#   walk_to(@thing)  | anim(name, ms) | wait(ms) | emit(event)  queued, e.g. Fell(pit) #
# A symbol is a pointer into the game's saved state, typed by what it holds: #
#   @room.lever(L) : Sym(Bool), @room.wiring : Sym(Wiring), @access.lever_far : Sym(Bool) #

let pull_room_lever = fun side : Side ->
  do far <- get(@access.lever_far) in
  do _ <- (if far then pure(()) else walk_to(@room.lever_thing(side))) in
  do up <- get(@room.lever(side)) in
  do _ <- set(@room.lever(side), !up) in
  do _ <- anim("lever-turn", 1400) in
  do wiring <- get(@room.wiring) in             # normal, reversed or random #
  do opened <- swing_pits(pits_worked(wiring, side)) in
  do at <- get(@friend.place) in
  if over_any(at, opened) then emit(Fell(at)) else pure(())
in

In the game today that is about 150 lines of JavaScript (the room's levers, its boulder levers, the placed levers' links, the walk to a lever and the pull, the pits' wiring). In Hazel, by estimate: the rules 60 to 90 lines; the monad's declaration in the builtins, as $UpdateCmd's is, 40; and in the game a command interpreter, about 100 lines of JavaScript, which keeps every animation and walk where it is now. Per pull, ~1 ms of Hazel (as measured above), the animations' time aside. What is new to Hazel: commands that suspend for the game, and symbols as typed pointers into a store Hazel does not own.

What it would take (^ticket(480)) for a Scripting panel in Dress Up, an editor per room, starting with the castle's dungeon:

  1. Hazel as a JS library, a second build entry beside the app's: analyze(text) and evaluate(text) on the page's own thread (rules this small need no worker), then mountEditor(element, {text, onChange, ...}), one code editor in any page. The editor assumes the whole app today (its settings, focus handling and keys at the document, its stylesheet unscoped), so that is the main work; and Dress Up's own keys move the friend, so keys must stay in the editor that has focus. About 7 MB of script, loaded only when the panel opens.
  2. One global program, composed from the panel's editors: module Common = {...} in module Dungeon1 = {...} in ..., each room's editor a module named by its room, Common in scope in all of them; Dress Up makes the names (and refuses a duplicate). #2469's modular editors, which #2635 carries, already show one program as a cell per definition: the closest start.
  3. The $GameUpdate monad (sketched above) as a builtin, and its interpreter in the game.
  4. The hook: on an event (a lever pulled, a room entered), the game asks the program's handler for that room and runs the commands it returns.

Order: 1's analyze/evaluate and 3 first, with the rules in plain text, which runs the dungeon's logic end to end; then the editor, then the panel.
