The three causes

1. Per-member module analysis meets Modules II (8 tests)

#2469's statics work per item: a top-level definition is analyzed on its own, and after an edit only the items it touches are analyzed again. Inside a module literal, #2469 goes further and works per member. Its DefStaticsParity tests count the units analyzed after an edit. For example, "item + 1 member re-analyzed" expects 2: the member and the item around it.

That per-member path reads modules through dev's module statics (value_exports, collect_type_exports, module_actual_type, and the labeled-tuple lowering). Modules II, which is on the livelits branch only, replaced those with signatures, sealing and abstract members. To make the merge build, 43089b065d (2026-10-01) has DefStatics analyze a module literal whole, as one item, and says so: per-member analysis "is off until it is rebuilt on Modules II". The trial merge on 10-17 (8c968efcc4) restates it.

So the counts come out low: the whole module is one unit, re-analyzed all at once, where #2469 would re-analyze one member and the item around it. The results are right. DefStaticsParity's other tests, which compare per-item results with whole-program results, pass on the merge. What is lost is granularity, which on a large module is a cost in time.

The rebuild has been done, on another branch. Andrew's #2687 ("Standard library in Hazel source", stdlib into modular-editors) has merged Modules II parts 1 and 2 (#2493 and #2494) since 10-16. In 00bc805ca1 (2026-10-18) he rebuilt the module part of per-item statics on Modules II. Members are lowered against the signature, the module's type is its signature type, and a signature the members do not meet still analyzes the item whole. His message measures "edits in mega-mod-1k wrapped or sealed in a module: ~100 → 7ms". #2687's CI has passed since 10-18, with every DefStaticsParity case named below present, their expected counts unchanged, and the corpus test still in: {{T87F}} tests in Fast checks and {{T87U}} in Full tests at 5cf71f2d30. #2635's Modules II is older, parts 1 to 3 as merged into the livelits branch on 09-16, so the port may need adapting to part 3 (abstract type members, sealing, path types). Under Cyrus's merge plan (What next, step 4), Andrew's modular editing PRs go into dev before the livelits PRs, so the livelits branch will take this rebuild from dev when it next merges dev, and adapt it to part 3 then if it has not been done already.

2. A livelits table test meets dev's canonical completion (1 test)

Editing.TableDecorations 1 ("typed table: hidden row error draws no arms, flags the chrome") puts a stray [ in a table cell. Its error then lands in a row the table hides, and the test checks that the table's chrome flags it. Since 2026-09-22 (#2374), dev's canonical completion closes a stray bracket where it stands. So the error lands in the cell, where it can be seen, and the chrome is right not to flag it: expected true, received false. The test needs an input whose error is really hidden. 11fbc4480d (2026-10-01) left it failing on purpose and says why.

#2469 does not cause this: it carries the completion only because it is based on a newer dev. The livelits branch #2597 is still on dev as of the morning of 2026-09-22 (2f9f2f6424, just before #2374), {{BEHIND}} commits behind. It will meet the same failure when it next merges dev.

3. One livelits document elaborates differently per item (1 test)

DefStaticsParity's corpus test ("the slide corpus through calc_auto") elaborates every program in the slide corpus twice, per item and as a whole program, and compares the two. One document differs: docs/livelits/expansion-errors/macro-result.hz, at a livelit application and at the let around it. A local run when the branch was made, on 10-01, found the per-item elaboration reading a + 2 where the whole-program one reads a + 1. The 2 is a literal whose source appears in no program, which suggests something carried over between documents in the corpus run. It has been listed among the branch's known failures since cefa5c2c5c (2026-10-10), and its cause has not been found. Of the ten failures, this is the one that may be a real bug rather than a known gap.

Update, 2026-10-19: the cause is found: after the corpus test's edit, a livelit use kept the expansion of the edited definition. See the update.

Update, 2026-10-19 at 12:45 MDT: a fix for each cause

  • The corpus document (cause 3): the corpus test analyzes each document, edits it (a 1 becomes a 2), analyzes it again, and then analyzes the original once more. On macro-result.hz that last analysis kept the edited expansion: ^^livelit(^inc(...)) elaborated to a + 2, where a cold analysis and monolithic statics both give a + 1. A use records the livelit it applies as ^inc among the names it depends on, but DefStatics named a livelit's own entry plain inc, so a changed livelit marked nothing stale. 1131a457e4 names it ^inc. The bug was in incremental statics, not in the test.
  • The table test (cause 2): 27f100e37c gives the row a wrong label (c, not bc): an error in table syntax that the projector hides, whatever completion does. The state from the original crash report, a stray bracket typed into a cell, is still drawn and checked. #2597 still has the old input, which will fail there at its next merge with dev.
  • The 8 module tests (cause 1): #2699 ports Andrew's per-member analysis on Modules II into #2635: his a6b5478f52, the form from before spans stage 6, which #2635 does not have (00bc805ca1 re-ported it onto stage 6), fitted to #2635's Modules II part 3. That cleared the 8, but its CI then failed the corpus test on another document, color-fig3.hz. A livelit definition, let ^color = { ... }, binds a variable, so the per-member path took it for a module and analyzed it member by member, skipping what Statics does with a livelit definition. 223357135a keeps a livelit definition whole. With #2635's fixes merged in, #2699 passes all 43 DefStaticsParity cases locally, and its Fast checks pass on GitHub.
  • The conflicts: cf325d4f61 merges the livelits branch into #2635, keeping #2635's side of every conflict, since each of #2597's commits since the merge base was already there. GitHub now shows #2635 as mergeable.
  • So, of the steps below: 1 is done through #2699, 3 and 5 are done, and 2 is done on #2635 but not yet on #2597.
